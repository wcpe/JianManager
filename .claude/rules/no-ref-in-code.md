# 代码禁止出现 FR / ADR 编号

> **编号只属于文档**（PRD / spec / ADR / CHANGELOG）。
> 代码、文件名、注释、字符串、标识符一律不写 `FR-NNN` / `ADR-NNN`。

## 为什么

编号是**文档内部的书目信息**，不适合出现在代码里。两类编号都不例外：

1. **会变**。需求重号要改号（见 [prd-authoring.md](prd-authoring.md) §5）；ADR 虽「永不复用」，但**会因重号而改号**——实测 2026-11-09 就发生过：`ADR-074` 同时被 Bot 分布式调度与发布溯源占用，发布溯源那篇改为 `ADR-108`（见 [docs/adr/README.md](../../docs/adr/README.md)）。代码里每写一处编号，改号时就要跟着改一处，且**改漏了没有任何编译错误**，只会留下指向不存在编号的死引用。
2. **不解释实现**。`// FR-431: 侧栏按权限裁剪` 相对 `// 侧栏按权限裁剪` 没多任何信息——想知道 FR-431 是什么，还得去翻 PRD。`// 参见 ADR-003` 同理：读者要理解这段为什么这么写，仍然得跳去读 ADR 全文。**注释该承载的是理由本身**，而不是理由的门牌号。

### 2026-11-09 修订：ADR 编号一并禁止

此前规则**只禁 FR、允许 ADR**，理由写作「ADR 编号回答的是『为什么这么选』，那才是注释该承载的东西」。
实测这个口子留下 **1,709 处**引用，且带来两个具体问题：

- **改号即失配**：ADR-074 同时被 Bot 分布式调度（2026-07-18）与发布溯源（2026-07-19）占用，2026-11-09 把后者改为 ADR-108。改号本身在 6 处文档链接上“全量同步”是可行的（那次实际做到了），但**若同一编号被代码引用，就要在编译错误看不见的地方逐处追**：代码里的 `ADR-074` 不会报错，只会静默地指向另一个决策。编号越密，这种失效越难发现。
- **可追溯性其实是假的**：`// 参见 ADR-003` 只有翻到 ADR 才知道决策是什么。把那一句决策理由直接写进注释，读者当场就懂，且不随文档编号变动而失效。

所以现在的口径统一为：**编号留在文档，代码写理由本身**。

## 规则

### 禁止

| 位置 | 反例 |
|---|---|
| 注释 | `// FR-486 范围③：复用扫描缓冲区`、`// 参见 ADR-003: 守护进程 Wrapper 模式` |
| 文件名 | `proxy_fr035_test.go`、`fr513-host-obs-visual.spec.ts`、`adr074-smoke.go` |
| 标识符 | `handleFR486Case()`、`TestFR397_ToolsRegistered`、`openFR370DB()` |
| 字符串 / 测试描述 | `it('FR-507 阶段6：…')`、`os.Getenv("JM_FR501_S3_AK")` |

> 环境变量前缀、测试函数名、临时路径（`.tmp/acceptance/FR-xxx/`）都算「字符串 / 标识符」，同样禁止。

### 允许

- **文档**：PRD / `docs/specs/**` / `docs/adr/**` / `CHANGELOG.md` —— 编号在那里才是有效信息
- `.claude/rules/**` 本身：规则需要举反例，必然出现编号
- **存量代码**：本规则出台前已存在的编号不动（见下方「执行范围」）

### 替代写法

想表达的东西只有三类，各有正确落点：

| 你原本想写 | 正确写法 |
|---|---|
| 这条需求的背景 | 写进 PRD / spec，代码里不引用 |
| 为什么这样实现 / 决策依据 | **把理由本身写出来**：`// daemon 启动必须经 Wrapper 子进程隔离——否则 Worker 重启会连带杀死运行中的游戏服` |
| 这段是新加的哪批工作 | 靠 `git blame` / commit message，不靠注释 |

**判断标准**：删掉编号后这句话还有没有信息量？没有就说明编号是唯一信息源，那就该改写成理由；有就说明编号本来就是多余的。

## 执行范围：只约束新增与修改

**存量不动。** 规则出台时代码里已有大量编号。全量清理是独立的一轮工作，不在日常改动里顺手做——那会把功能提交搅成噪音。

判定方式：**只检查本次 diff 新增/修改的行**。存量行原样保留，即使它就在你改的那个文件里。

```bash
# 门禁做法（见 scripts/check-no-ref-in-code.sh）
# 只扫 `git diff <base>...HEAD` 的 `+` 行，存量不参与
```

## 门禁

`.claude/scripts/check-no-ref-in-code.sh`：

| 模式 | 命令 | 用途 |
|---|---|---|
| diff（默认） | `sh .claude/scripts/check-no-ref-in-code.sh` | 只扫 diff 的 `+` 行，命中即失败并打印位置。日常提交前跑 |
| 存量 | `sh .claude/scripts/check-no-ref-in-code.sh --stock` | 扫全仓代码现有编号，**期望 0 命中**。全量清理的验收就是这个 |

扫描范围：`apps/` `internal/` `packages/` `scripts/` `proto/` `client-updater/` `configs/`（生成文件 `*.pb.go` 除外）。
其中 `scripts/fr-acceptance/` 整目录豁免（见上方「目录级豁免」）。

配套 CI 步骤在 [gate-merge.md](gate-merge.md) 的静态检查项里。

**误报例外**：文档路径（`docs/`、`CHANGELOG.md`）与 `.claude/rules/` 本身不在扫描范围。
若确有必需保留的场景（例如迁移脚本要按旧编号匹配历史数据、测试夹具要复现线上环境变量名），在该行加
`// no-ref-check: <原因>` 豁免，并在 PR 描述里说明。

### 目录级豁免：`scripts/fr-acceptance/`

验收工具目录**整目录豁免**。理由不是「麻烦」，是**这里的编号不是注释、而是数据主键**：

```python
v1 = Verdict('FR-506', '采集游标跨重启持久化')   # FR-506 是这个用例的身份
```

删掉它，`pending.py` 就失去统计能力（它正是靠扫 `FR-(\d+)` 得出「82 条里哪些已被断言过」）。

这与规则要防的失效模式不同。规则防的是：**注释写了个编号当门牌号**，号一变注释就成了死引用，
而且**没有任何编译错误**提醒你。而验收脚本里的编号有机器消费者——改号时统计会归零、
下一步立刻被发现，不会静默失效。

判断标准：**这个编号有没有机器读者？**

| 情形 | 结论 |
|---|---|
| 注释里写 `// FR-486 复用扫描缓冲区`，只是标注归属 | ❌ 违规，改写成理由 |
| 数据字段 / 用例主键 / 断言参数，程序会读它 | ✅ 豁免（仅限验收工具目录）|

豁免仅限 `scripts/fr-acceptance/` 一个目录。生产代码（`apps/` `internal/` `packages/` `proto/`
`client-updater/` `configs/`）**照旧要求 0**，不因本条款放宽。

## 自检

- [ ] 本次新增/修改的注释里没有 `FR-\d+` 与 `ADR-\d+`
- [ ] 新增文件名不含 `fr\d+` / `adr\d+`
- [ ] 测试描述（`describe` / `it` / `t.Run`）与测试函数名不含编号
- [ ] 需要决策依据时，写的是**理由本身**，不是编号
