# PRD 书写规范

> PRD 是**需求登记册**，不是变更日志、不是验收报告、不是实现说明。
> 本文约束「怎么把一行 FR 写对」，配合 [gate-prd.md](gate-prd.md)（能不能进 SDD）与
> [doc-evolution.md](doc-evolution.md)（三种文档的演进方式）一起看。

## 0. 一句话判据

**一行 FR 只回答「要做什么」，其余一切（怎么做、做到哪、证据是什么）都属于 spec。**

写完自查：把这一行给一个没参与开发的人看，他应该能说出「这个功能是干什么的」，
而**不需要**读懂任何实现细节；反过来，他也不该从这一行看出「做完了没有、验收到什么程度」。

## 1. 四个字段各只干一件事

`| 编号 | 需求 | 优先级 | 状态 |`

| 字段 | 只写什么 | 明确不写 |
|---|---|---|
| 编号 | 唯一、递增的 `FR-NNN` | 复用、重号、范围占位 |
| 需求 | **功能是什么**（WHAT），≤150 字符为宜、**硬上限 300** | 实现细节、交付状态、变更历史、验收清单 |
| 优先级 | `P0`/`P1`/`P2`；已交付/已废弃后记 `—` | 用优先级表达状态 |
| 状态 | 标记 + 版本（+ 简短验收档位后缀） | 括号长说明、缺陷清单、真机取证 |

### 需求列**禁止**出现的四类内容

这四类是 PRD 退化的主因，每一条都对应一次真实踩坑：

1. **实现细节** —— 文件路径、函数名、字段名、算法、proto 改动。
   > ❌ `...改为经 Worker 主动建立的常驻双向流承载——含 proto 新增双向指令流、CP 连接池由「拨号」改为「往流里派发 + 关联请求/回执」...`
   > ✅ `CP→Worker 指令反向流化（免 NAT / 零入站端口暴露）`

2. **交付状态** —— 「已落地」「已实现」「真机验证」「修掉 N 个缺陷」「测试全绿」。
   > ❌ `...（**执行层已接通，真机验收通过**）：工具登记表从 agentActionCatalog 派生...过程中修掉 6 个真实缺陷...`
   > ✅ `受限系统工具与逐调用写入确认`

3. **变更历史** —— 「原计划…」「后改为…」「此前误标…」。
   历史属于 CHANGELOG 与 git；PRD 只描述**当前**的需求。

4. **验收清单** —— 大段「验收：①…②…③…」。
   验收标准是 spec 的核心内容；PRD 里放不下也不需要放。

### 状态列怎么写

```
✅ 已交付@v0.24.0              ← 必须带版本号（见 gate-prd.md）
🔨 开发中                      ← 不得自标已交付
📋 计划 / ⏸️ 已延后 / ❌ 已废弃
✅ 已交付@v0.15.0·全真栈验收    ← 可留 PRD §4 图例里定义的档位后缀
```

**不得**写括号长说明：
> ❌ `✅ 已交付@v0.15.0·真机验收（现网双反向隧道自愈、隧道承载探针/上传/终端中转、NAT 场景真跑）`
> ✅ `✅ 已交付@v0.15.0·真机验收`

## 2. 表格的硬约束（会静默破坏渲染）

- **一行一个 FR，不得有续行**。用「表格行 + 缩进续行」写长内容，会让续行脱离表格变成正文，
  同时把该行 FR 的列结构打断——渲染出错但 markdown 语法**不报错**，只能靠肉眼或脚本发现。
- **单元格内的字面 `|` 必须转义为 `\|`**。裸 `|` 会被当成列分隔符，
  直接把 4 列切成 5 列。典型来源：`精确|近似`、`curl|bash`、`a/b|c` 这类并列写法。
- **表格内不得有注释/说明段落**。要说明的事写进 spec 或表格上方的引用块（`>`）。
- **§4 主表按编号升序**。逆序不影响渲染，但让「扫描是否有重号/缺号」变得困难。

## 3. 规格索引段怎么写

§4 表格上方的「活跃 FR 详细规格索引」是**导航**，不是摘要：

```
- FR-521～528（2026-10-23 业务能力退役与对外通道重构）→ `docs/specs/business-capability-retirement/spec.md` 等 6 个 spec
- FR-489（2026-09-28 MCP 端点无状态化与 Token 维度运维视图）→ `docs/specs/mcp-stateless-endpoint/spec.md`（+ ADR-096）
```

- 只留：**FR 范围（日期 主题）→ spec 路径**
- **不记状态**（状态在表里，写两遍必然漂移）
- **不写实现细节与决策理由**（那些属于 spec / ADR）
- 免 spec 的批次显式写「**七项均免 spec**」，别让人以为漏登记

## 4. 取证明细写到哪里

| 情形 | 落点 |
|---|---|
| 有 spec | 该 spec 的「实现状态 / 验收」节 |
| 免 spec 的 FR | `docs/specs/unspecced-fr-records/spec.md`（按 FR 分组，保留原文） |
| 有架构决策 | ADR（**只追加不删改**，见 [doc-evolution.md](doc-evolution.md)） |
| 交付了什么、修了什么 | CHANGELOG |

**迁移历史内容时不要改写原文**——迁入是为了让 PRD 可读，不是为了重述历史。
改写会让「当时的证据」变成「现在的转述」，追溯性直接消失。

## 5. 编号管理

- **唯一**。发现重号时，**改「引用面更小」的那个**——先 `grep -rn "FR-NNN" docs/ CHANGELOG.md` 数引用，
  改被引用少的一方；命名体系里的号（spec 文件名、代码注释）动了就是大面积返工。
- **新增 FR 取当前最大号 +1**，不跳号；**已合入 master 的废弃号不得复用**（该号已进历史，复用会把「同一号两段历史」带进外部引用）。分支上同批规划中途撤销的号可以回填，因为尚未合入主线、无人依赖。
- **改号必须在 CHANGELOG 记一笔**（原号 → 新号 + 原因），否则外部引用会永久歧义。
- 范围写法 `FR-521～528` 只能用来说明「这几项同属一批」，**不能代替逐个登记**。

## 6. 常见退化与对应判据

评审 PRD 时按这张表扫，命中即要求整改：

| 现象 | 判据 | 处置 |
|---|---|---|
| 需求列写成实现说明 | 含文件路径 / 函数名 / proto 字段 | 截到「标题（目的）」为止，其余迁 spec |
| 需求列记状态 | 含「已落地/已实现/真机/修掉/测试全绿」 | 同上 |
| 状态列带长括号 | 状态单元格 > 40 字符 | 只留标记 + 版本 + 档位 |
| 表格被撑破 | 有续行，或单元格含裸 `\|` | 合并为单行 / 转义 |
| 索引段写状态 | 含「已交付@v」/「✅」 | 删状态，留 spec 链接 |
| 编号重号 | `grep -oP '^\| FR-\K\d+' docs/PRD.md \| sort \| uniq -d` 非空 | 改引用面小的一方 |
| 编号乱序 | 表内出现降序 | 整段按号排序 |

自查脚本（可粘进 shell）：

```bash
# 注意：§4 主表到「### 范围外」为止，其后是独立的「范围外」表（FR-100 等），
# 两者编号体系不相干——下面的脚本必须先截断，否则会把跨表跳号误报成逆序。

# 重号（应为空）
sed '/^### 范围外/,$d' docs/PRD.md | grep -oP '^\| FR-\K\d+' | sort -n | uniq -d
# 逆序（应为 0）
sed '/^### 范围外/,$d' docs/PRD.md | grep -oP '^\| FR-\K\d+' | awk 'p>$1{c++} {p=$1} END{print c+0}'
# 超长需求列（>300 字符；注意含转义 \| 的行长度会偏大，需人工确认）
sed '/^### 范围外/,$d' docs/PRD.md | awk -F'|' '/^\| FR-/{ if (length($3)>300) print $2, length($3) }'
# 表格续行（不以 | 开头却以 | 结尾）
grep -nE '^[^|#>-].*\|$' docs/PRD.md
```

## 7. 为什么这些约束值得守

PRD 的读者有三类，它们的诉求不同：

- **规划者**要在一屏内扫完「有哪些需求、各自什么状态」——所以表格必须能扫。
- **开发者**要顺着 FR 找到完整规格——所以索引段必须有 spec 链接。
- **后来者**要能追溯「当时怎么验的」——所以取证明细必须完整保留在 spec 里。

一行 FR 塞进实现细节时，前两类读者被挤走；把取证从 spec 里删掉只留在 PRD 时，第三类失去依据。
**本文所有约束都是在保护这三类读者各自的入口**，不是为了格式好看。
