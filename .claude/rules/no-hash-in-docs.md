# 文档禁止写 git commit hash

> **文档里不要写 `xxxxxxxx` 形式的提交 hash。**
> 仓库用 **squash merge**，分支提交合并后 hash 不会保留——写进文档就是一批注定失效的死引用。

## 为什么

squash merge 会把分支上的一串提交压成一个新提交，丢弃原有 hash。于是：

- **写的时候能解析，合并后就查不到了**——读者 `git show <hash>` 直接报错；
- **更隐蔽的是悬空**：本机对象库里残留时还能查，别人 clone 下来就没了；
- **没有任何门禁会报错**：不像代码引用有编译错误，文档里的死引用永远静默。

2026-11-10 实测：仓库文档里曾累积 **82 处**这类引用，其中 12 个 hash 在本地尚可解析但**不在 `origin/master` 主线历史里**（squash 后必然悬空），其余多数已彻底查不到。

## 正确写法：用「提交标题 + 日期」定位

| ❌ 不要写 | ✅ 改成 |
|---|---|
| 「提交 `<hash>` 覆盖了 PRD」 | 「那次『同步 master 侧文档更新（PRD 状态滞后 115 条）』的提交」 |
| 「`<hash>` 引入 FR-502~512」 | 「2026-11-09 那次『日志采集改 tailer / VL 唯一事实源』的提交」 |
| 「父提交 `<hash>`」 | 「它的父提交」 |
| 「落地提交：`<hash>`」 | 「落地（提交见 git log）」 |
| 「（commit `<hash>`，已部署生产）」 | 「（PR #24，已部署生产）」 |

**可追溯性不损失**：提交标题 + 日期唯一，`git log --grep '<标题片段>'` 照样能定位；反倒是 hash 在 squash 后永久失配。

批量列举时也不要逐个写 hash：

```
❌ FR-283 `<h1>`/`<h2>`/`<h3>`/`<h4>`；FR-285 `<h5>`
✅ FR-283 分四步（骨架 / 依赖接线 / Tailwind / 抽包）；FR-285 抽尾（提交见 git log）
```

## 允许出现的东西（不是提交 hash）

扫描时短十六进制串很多是误报，**下列不算违规**：

| 类型 | 例子 |
|---|---|
| 内容/树 SHA | 文件 sha256、`canonical_content_hash`、git tree hash |
| 业务错误码 | `40034105`（QQ 平台）、`SQLITE_CANTOPEN` |
| PID / 端口 / 行号 | `2074628`、`512` |
| 字节数 / 纳秒 | `67108864`、`719532125` |
| 文档示例占位 | `abcdef0`、`abc123def456` |
| 代码标识符 | 包名、字段名、`ed25519` |

内容哈希若必须写入，**加定语避免歧义**：「两种内容哈希 `xxxx` vs `yyyy`」。

## 门禁

`.claude/scripts/check-no-hash-in-docs.sh`：

| 模式 | 命令 | 用途 |
|---|---|---|
| diff（默认） | `sh .claude/scripts/check-no-hash-in-docs.sh` | 只扫 `git diff <base>...HEAD` 增行里的 md，命中即失败 |
| 全量 | `sh .claude/scripts/check-no-hash-in-docs.sh --all` | 扫全仓 md，**期望 0 命中** |

扫描范围：`*.md`（包 `docs/`、`CHANGELOG.md`、`README.md`、`.claude/`）。

**误报处理**：若某行确实是内容哈希/错误码被误判，在该行末尾加 `<!-- no-hash-check: <原因> -->` 豁免。

## 执行范围

- **新增/修改的行**：必须遵守，门禁只扫 diff。
- **存量**：已于 2026-11-10 全量清理完毕（当时 82 处）。今后无需再办一次性清理。
