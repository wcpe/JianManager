# 实例异常分级排查

不要一上来就重启。按下面顺序取证，每一步都要拿到**数据**再往下走。

## 1. 先确认「现在的状态」而不是「用户以为的状态」
- 调用 `system_agent_list_instances` / 实例详情，确认 `status` 与 `statusReason`。
- `statusReason` 是自由文本备注，常直接写着原因（崩溃退出码、未绑定 JDK 等）。
- 若状态与用户描述不一致，先说明差异，不要顺着用户的假设排下去。

## 2. 崩溃看趋势，不看单次
- 调用崩溃快照与崩溃趋势工具（`instance_list_crash_snapshots`、`instance_crash_trend`）。
- 只在趋势里找**重复的根因**；单次崩溃多为偶发，优先看近 7 天同类计数。

## 3. 用日志定位时间点，不要全文搜关键字
- 先取实例最近日志（`agent_get_instance_logs`）确认退出前最后几行。
- 需要更早的时间窗时走日志平台查询，按 `instance` 与时间范围收窄，不要拉全量。

## 4. 排除资源类原因
- 配额（`instance_quota_status`）：确认是否被 CPU/内存/磁盘限额强制。
- 节点：`node_get_metrics` 看该节点是否整体过载；同节点多实例同时异常，优先怀疑节点。

## 输出要求
- 结论必须区分「已证实」与「待确认」，并给出各自的取证手段。
- 需要改动（启停、改配置、换二进制）时**先说明影响面**，再走确认流程；
  写操作一律经用户逐次确认，不得自行连续执行多个写操作。
