# 策略与诊断

## 授权模型

三件事共同决定一次调用是否放行，缺一不可：

1. **capability**（能力分组）——如 `instance.read`、`instance.life`、`instance.destructive`
2. **scope**（作用域）——你能碰哪些节点/实例
3. **策略版本**——V1 用写白名单，V2 用 capability 分组

`agent_whoami` 会返回你的策略版本、能力与 scope。**先看它，再看工具列表。**

## 关键规则

### tools/list 只列你可能用得上的工具

`tools/list` 已按你的 capability 与潜在 scope 裁剪过。看不到某个工具，通常意味着：
- 你没有对应 capability，或
- 你没有该资源类型上的任何 scope

这不是服务端故障。不要试图猜测工具名盲目调用——未登记的工具一律拒绝。

### 拒绝是收敛的

对 agent，以下三种情况返回**同一个 403**：

- 资源不存在
- 资源存在但在你的 scope 外
- 有 scope 但缺 capability

这是有意的信息收敛，防止 agent 成为跨 scope 的存在性探针。
**不要通过反复变换 ID 来区分这三种情况**——那正是设计要阻止的行为。

### 拒绝的返回形态

策略拒绝 = **HTTP 200 + `result.isError=true`**，正文是中文原因。

```
✓ 正确：看 result.isError 或文本是否有拒绝原因
✗ 错误：看 HTTP 状态码判断成败
✗ 错误：把 isError 当成临时故障后重试
```

重试不会改变授权结果。若确实需要更多权限，告诉用户需要哪个 capability 或 scope 变更，
由人工重新签发 Token（能力与 scope 不支持在线编辑）。

### 节点 scope 单向覆盖实例（仅 V2）

V2 Token 若持有某节点 scope，则该节点上**当前与未来**的实例都在你的 scope 内。
实例移出该节点后自动失权。V1 Token 不启用此继承。

## 诊断顺序

调用失败时，按此顺序定位，不要跳步：

1. **`agent_whoami`** — 确认策略版本、能力、scope 是否符合预期
2. **`tools/list`** — 确认目标工具是否可见
3. **权限类原因** → 对比工具所需 capability 与 whoami 返回的能力
4. **参数类原因** → 确认必填参数与确认字段
5. **目标不符** → 重新查询目标真实 ID 与名称

## 常见原因对照

| 现象 | 原因 | 处理 |
|---|---|---|
| 工具不在 `tools/list` 中 | 缺 capability 或 scope | 告知用户需追加的能力/scope |
| `isError` + "无权限" | capability 或 scope 不足 | 同上，不要重试 |
| `isError` + "确认名称与目标不符" | 确认参数与真实名称不一致 | 重新查真实名称后再试 |
| `isError` + "缺少必填确认参数" | 未传 `confirmInstanceName` 等 | 补齐确认参数 |
| 返回 401 | Token 无效/过期/已吊销 | 提示用户重新签发，不要重试 |
| 实例/节点查不到 | 可能不在 scope 内 | 不要据此断定资源不存在 |

## 不该做的事

- **不要用 `config_*` / `file_*` 绕过业务校验。** 直接改配置看似"等效"，但会绕过状态机与审计，
  可能导致实例进入无法恢复的状态。
- **不要伪造工具调用。** 客户端缓存或构造的工具列表不参与服务端授权；
  `tools/call` 始终重新做最终授权。
- **不要在 isError 后自动换一个 ID 重试**，用以探测资源是否存在。
- **不要在收到拒绝后静默降级**成别的写路径完成任务。拒绝就是拒绝，向用户报告。
