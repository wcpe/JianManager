# 日志系统架构审计：与 VL 官方能力的差异清单

> 配套文档：`docs/logs-vl-capability-matrix.md`（官方能力实测对照表）
> 本文只做诊断与取舍判断，不含实现方案。

## 一、当前架构的三层补救

分区目录（「哪些天有数据」）是查询侧的第一道判据。它现在的真相链有三层：

```
第 1 层  Catalog journal —— 纯内存 + JSONL 落盘（catalog.NewBatchedStore）
            启动时 NewJournalWithStore 重放 → Catalog.records
第 2 层  ensureCatalogPartition —— 投递成功时补建「本批数据涉及的天」
            只在有新数据写入时触发
第 3 层  BackfillCatalogPartitionsFromVL —— 启动后异步跑一次，从 VL 反推 30 天
            每源一次查询，覆盖「从来没被写进 journal」的天
```

**这三层都是为了回答 VL 已经知道答案的问题。**
而 VL 的 `hits` 一次请求就能给出全部 (源,天) 分布（实测 372 个分区 / 217ms / 31KB）。

## 二、差异清单

### D1. 分区目录用副本代替事实来源 —— 缺陷（P0）

| | 现状 | 官方做法 |
|---|---|---|
| 事实来源 | 自己维护的 Catalog.records | `hits` 直接问 VL |
| 持久化 | JSONL journal + fsync | 不需要 |
| 一致性 | 副本可能与 VL 不一致 | 无副本，天然一致 |
| 恢复能力 | 依赖 journal 完整性 + 回填兜底 | 每次启动都是完整事实 |

**证据（本次事故链）**：
- journal 是纯内存时 → 重启后历史天全丢 → 日志页整页为空
- 改成落盘后 → 生产 journal 只写到 10-30，11-01/11-02 的记录**从来没被写进去**
  → 于是又加了第 3 层回填

⇒ 三层补救都源于「副本」这一个前提。去掉副本，三层同时消失。

**另有架构冲突**：落盘与 2026-10-30「机械盘不做落盘」的裁定直接冲突，
该裁定是被一次事故修 bug 顺手推翻的，而非经决策确认。

### D2. 回填窗口与实现效率 —— 低效（P0 的附带结论）

`BackfillCatalogPartitionsFromVL` 当前形态：
- 窗口固定默认 30 天（超出则漏）
- **每源一次查询**（19 源 = 19 次 HTTP）
- 天桶用 `stats by (_time:1d)`，在 Go 侧归天

`hits` 形态：
- 窗口任意（受 `maxQueryTimeRange=4344h` 约束，约 181 天）
- **一次查询拿全部源**
- 天桶由 VL 计算，`offset` 控制时区口径

⇒ D1 修好后 D2 整体删除。

### D3. Fields 从返回行猜字段名 —— 缺陷（P1）

```go
// vlrange/client.go Fields()
res, err := c.Search(ctx, rng, q)      // 拿一页行
for _, ev := range res.Items {
    for field := range ev.Fields { set[field] = ... }   // 从行里猜
}
```

后果：返回的是「**本页那几条日志恰好带的字段**」，不是该时间窗的字段全集。
实测：我们返回 `[level, stream]` 两项，而 `field_names` 显示该窗口有 15+ 个字段。

**为什么现有实现看起来「能过」**：契约只要求「字段名列表」，没要求完整性，
测试也就只断言「包含某个字段」。这是**契约本身留了模糊空间**。

### D4. Facets/Stats 自建聚合 —— 优化（P2）

- 我们：遍历 plan.Ranges → 每 range 一次 LogsQL `| stats` → 内存累加
- 官方：`facets` / `field_values` / `stats_query_range` 一次聚合

实测两者数值一致（INFO 4699 / WARN 546 / ERROR 31），
所以**不是错误，是多绕了一圈**。收益：少 N-1 次扇出、少一段 NDJSON 解析。

### D5. streams 系列完全缺失 —— 能力缺口（P3）

当前无法回答「这个时间窗有哪些 stream / stream 字段有哪些」。属于产品缺口，非缺陷。

### D6. 分页保持自建游标 —— 合理取舍（不改）

官方 `limit + offset` 是简易分页，数据变动时会漂移；
我们的复合排序键游标保证跨页无重无漏。**明确保留**，写进决策文档避免后人误改。

### D7. 天界口径必须写死 —— 风险项

VL 从**事件时间戳**推天界；`hits` 的 `offset` 参数会平移桶边界。
我们的分区键是 **UTC 日** ⇒ **绝不能在 hits 调用里传 offset**。

实测对照（同一份数据）：
```
不传 offset（UTC）: 11-01=2880  11-02=1746  11-04=890
offset=8h（HKT）  : 11-01=2706  11-04=1663
```

⇒ 这是历史上三次「天界」事故的同款根因。改造后必须在代码里加注释 + 测试锁死。

### D8. probe 探针数据会污染 hits 结果 —— 实现注意

实测 `hits` 返回 31 个源，其中 11 个是 `probe:*`（测试探针写入），
不属于平台管理的实例源。重建分区目录时**必须按已登记源过滤**。

## 三、取舍结论

| 编号 | 判定 | 处置 |
|---|---|---|
| D1 | 缺陷 | **本轮做**，P0 |
| D2 | 低效 | **本轮删除**（D1 的附带结果） |
| D3 | 缺陷 | 本轮做，P1 |
| D4 | 优化 | 记录为技术债，不在本轮 |
| D5 | 能力缺口 | 记录，按产品需求排期 |
| D6 | 合理取舍 | **明确保留**，写进决策文档 |
| D7 | 风险 | 实现时锁死 + 加测试 |
| D8 | 实现注意 | 实现时处理 |

## 四、本轮改造的边界（明确不做的事）

1. **不动 owner/generation/dirID 的权威判定**。`hits` 只提供「哪天有数据」这个物理事实，
   权威仍必须由 `Catalog.WriteAdmission` 决定。不能因为 VL 有数据就伪造权威。
2. **不动查询路径的 protocol**。`hits` 只允许在启动期/周期性跑，绝不进用户查询链路
   （否则每次查询多一次 VL 往返）。
3. **不动分页游标语义**（D6）。
4. **不动 Stats/Facets 的 wire 契约**（D4 只记录不实施）。

## 五、改造过程中新发现的问题（2026-11-05 实测）

### D9. 过时假设把正确的实现限制成了错误的 —— 缺陷（已修）

代码里多处注释写着 **「`-search.maxQueryTimeRange` 是 31d」**，并据此设了两个常量：

```go
DefaultCatalogBackfillDays = 30      // 回溯窗口
catalogBackfillMaxRange   = 30*24h   // 单次查询跨度
```

**但实际启动参数是**（`ps` 实测）：

```
-retentionPeriod=180d  -search.maxQueryTimeRange=4344h(=181d)
```

二者的关系是 `maxQueryTimeRange = retention + 1d`（见 `vlsup.BuildArgs`）。
也就是说 **31d 这个前提早已不成立**，30 天是自己加的限制，不是 VL 的要求。

#### 后果（生产实测）

清空 journal 后让 hits 独立重建分区目录：

```
facts=311  created=300  skipped=11  failed=0     ← 30 天窗口
```

对比旧 journal 的分区集合：

```
旧 journal:  388 个分区
hits 补回:   300 个
缺失:         88 个，全部落在 2026-09-20 ~ 2026-10-06
```

而那 88 天 **VL 里确实有数据**：

```
inst:317 / 2026-09-20 → 11562 条
inst:317 / 2026-09-21 → 29422 条
```

⇒ 窗口设小不是「保守」，而是**直接丢掉能查到的历史**。

#### 更值得注意的一点

180 天窗口下，`inst:317` 有 **37 天**数据，而旧 journal 只有 **32 天**。

journal 只在「分区状态变化」时写一条，会漏掉一些天；hits 直接问 VL，覆盖更全。
⇒ **hits 不只是「替代」journal，它在完整性上更强。**

#### 修法

| 常量 | 原值 | 现值 | 依据 |
|---|---|---|---|
| `DefaultCatalogBackfillDays` | 30 | **180** | 与默认 retention 同量级，仍 < 181d 上限 |
| `catalogBackfillMaxRange` | 30d | **90d** | 切窗粒度，低于上限且少一半往返 |

#### 顺带修正了一条**本身有缺陷的**测试

原用例断言「默认窗口总跨度 ≤ 单段上限」。窗口改大后它必然失败——
但**这条断言守的东西是错的**：回填是**切窗后逐段查询**的，总窗口本来就可以大于单段上限。

真正要守的是「切出来的每一段都不超上限」。已拆成两条：
- `TestBackfillDaysWindow_Bounded`：默认值语义 + 「总窗口应大于单段上限」（证明切窗有意义）
- `TestBackfillDaysWindow_SegmentsBounded`：逐段校验不超上限，且至少切成 2 段

### 教训

**注释里的技术前提会过期，而过期的前提会把正确的实现锁成错误的。**
这次审计的价值不在“发现新 API”，而在**核对既有假设是否还成立**。
凡注释里出现具体的数值前提（上限、默认值、版本号），都该有一条用例或一个判据把它钉住，
否则它只会在下次读到时误导人。
