# 功能规格：ServerProbe 本地上传来源

> 状态：已交付@v0.21.0　·　关联 PRD：FR-411　·　关联 ADR：ADR-085

## 1. 背景与目标

当前 ServerProbe 版本库仅能从 GitHub Releases 同步。管理员需要把本地持有的 JAR 纳入同一版本库，并在版本页面明确区分“线上拉取”和“本地上传”，以便选择、回滚和排查来源。

本功能在既有 CAS 制品库与“制品包 / 来源 / 版本”模型上扩展；不修改 ServerProbe 仓库，也不改变 CP 向 Worker 下发制品的路径。

## 2. 需求（要什么）

- ServerProbe 制品包新增一个内置来源 local-upload，展示名为“本地上传”；既有 GitHub Releases 来源展示为“GitHub Releases（线上拉取）”。
- 平台管理员可在 ServerProbe 版本库页面提交 version 和一个 .jar 文件。文件最大为 64 MiB。
- CP 流式接收文件并写入现有 CAS；服务端自行计算 SHA-256 与 MD5，不采信客户端摘要。
- 上传成功后立即创建一个已缓存版本，可被现有全局、Worker、实例版本选择逻辑使用。
- 同一“本地上传”来源内版本号不得重复，重复时返回冲突；本地来源与 GitHub 来源允许具有相同版本号，页面必须显示来源以消除歧义。
- CAS 内容相同的线上与本地版本复用同一资产实体，但两条版本记录仍各自保留来源。
- 上传不自动修改全局默认版本，也不影响已有实例。
- 版本页为每个来源和版本显示友好来源标签；仅 GitHub Releases 来源提供“同步”操作，本地上传来源不显示同步操作。

范围内：平台管理员上传 ServerProbe JAR、版本来源标识、已有版本选择链路复用。

不做（范围外）：其他外部来源、来源凭证、从 CP 本地路径导入、通用资产上传入口、签名或字节码校验、自动设为全局默认、自动升级旧实例、ServerProbe 仓库改动。

## 3. 设计（怎么做）

实现前新增 ADR-085，明确把 local-upload 作为 ArtifactSource.Provider 的第二种来源；其余 CAS、版本选择与 CP→Worker 拉取协议保持不变。

- 在 ServerProbe 目录初始化时确保存在唯一的“本地上传”来源；复用现有 ArtifactSource、ArtifactVersion、Asset 表，不新增数据库表。
- 新增仅平台管理员可访问的 multipart 接口：POST /api/v1/artifact-packages/serverprobe/versions/upload。
  - 请求字段：version、file。
  - 成功：201 并返回创建的版本。
  - 缺少字段、版本号无效、非 .jar 文件：400。
  - 超过 64 MiB：413。
  - 本地来源内版本号已存在：409。
- 后端复用现有 AssetService.Ingest，以 server-probe 类型写入 CAS。创建版本时写入 ReleaseRef=local-upload、AssetID、CachedAt、服务端计算的 SHA-256，以及仅作溯源用的 local://upload/<asset-id>。
- 上传流程在现有版本服务互斥范围内执行“查重 → 写入 CAS → 创建版本”，避免并发请求产生重复版本；CAS 自身仍负责同摘要资产去重。
- 前端使用 FormData 调用上传接口；上传成功后刷新版本目录与可选版本列表。来源标签从版本关联的 SourceID 推导，绝不根据共享资产的来源 URL 推导。
- Worker、协议定义及实例版本下发接口无需改变：本地上传版本已有 AssetID，因此沿用现有 CP 短时下载地址和 Worker 拉取流程。

## 5. 验收标准

- 平台管理员上传合法 .jar 与 0.1.0 后，API 返回 201；目录中出现“本地上传 / 0.1.0”，且 SHA-256 由服务端计算。请求必须先传完整 `version` 字段、再传 `file` 字段，服务端不得物化整个 multipart 文件或使用 `FormFile`。
- 同一文件先作为线上版本缓存、再上传为本地 0.1.0 时，两条版本记录的来源不同、可复用同一 CAS 资产，且全局默认版本不发生变化。
- 非管理员不能上传；缺字段、非 JAR、超限文件和重复本地版本分别得到明确的失败响应。
- 页面同时可辨认“GitHub Releases（线上拉取）”与“本地上传”；本地上传来源没有同步按钮。
- Worker 选择本地 0.1.0 后能从 CP 获取制品并使测试实例完成首次启动；随后可切回线上 0.2.0。
- 修复后的目标环境验收需重新执行。0.1.0 是对现有 JAR 的副本，因此该验收验证来源、选择与下发链路，不证明不同代码版本的行为差异。

## 6. 风险 / 待定

- 64 MiB 是本次上传上限；如后续制品显著增大，应在独立需求中调整并评估反向代理限制。
- 用户要求的 0.1.0 测试副本将在验收后保留为本地来源版本；不自动设为默认。
