## 3. 过程中发现的量测缺陷（已修正，非产品缺陷）

首轮真机运行报出「每次恰好一个源卡住」：该源 `durable_position` 已推进、
但 `delivery_position=0`、`delivery_state=NOT_SENT`、WAL 未裁剪，`state.json` 达 3.3 MB。

**根因在量测脚本**：它只 `cancel()` 采集循环就退出，**从不调用 `Manager.Stop()`**——
而 `Stop()` 才做最终 `Flush()`（闭合尾行）+ `persist()`。因此磁盘上的 `state.json`
停留在**采集循环的中途快照**，把「投递尚未完成」误读为「卡住」。
修正为 `Stop()` 后：8 源场景 `state.json` 由 3.3 MB 降到 22.1 KiB、8/8 源 `REQUEST_DONE`。

同时修正了完成判据：原用「段文件数 ≥ 源数」判定采集完成，但**落段发生在投递之前**，
会过早判定完成并读到中途快照。现改用 `CutoverReadiness()`（按源检查
`durable>=read` 与 `reclaim>=durable`），即「投递已记账、回收已推进」的完整信号。

> 这与阶段 5 的教训同源：**量测脚手架的行为会被误记为被测对象的行为**。
> 两次都是靠「独立交叉验证 + 剖析归因」而非相信单一读数发现的。

### 3.1 复现证据与残余风险（保留以免被误判为产品缺陷）

缺陷判定的直接依据（原始 `ingest.state.json` 留在 `.tmp/fr444-acceptance/{r1,r2,r3,r1-restart,root64}`，不入库）：

| 场景 | 源数 | 观测 |
|---|---|---|
| r1 | 8 | 卡住源 `:6`，WAL 2999 条、`delivery_state=NOT_SENT`、`delivery_position=0`，state 3.43 MB |
| r2 | 8 | 卡住源 `:8`，state 3.43 MB |
| r3 | 8 | 卡住源 `:2`，state 3.42 MB |
| root64 | 8 | 卡住源 `:7`，state 3.44 MB |
| r1-restart | 8 | 重启后 state 降到 **21 981 B**、WAL 清空（自愈） |

**每次恰好一源、位置随机**，且该源在真 VL 中事件数已达 2999 —— 即「数据未丢、仅记账未落」。
修正 harness（补 `Stop()` + 改用 `CutoverReadiness` 判据）后复测：8 源场景 **8/8 `REQUEST_DONE`**、
state 22.1 KiB、卡住源消失，证实为**快照时机**问题而非投递缺陷。

**残余风险（未完全排除）**：上表仅证明「只 `cancel()` 不 `Stop()`」会产生该读数，
**未**用产品代码路径（正常 `Stop()`）复现过任何「投递已发生但记账永久丢失」的情形；
真机 342 源逐一核对也显示零丢失零重复。故判定为 harness 缺陷。
但「投递完成与 ledger 记账之间存在窗口」这一结构性事实仍成立——若进程在该窗口内
被强杀（而非优雅 `Stop()`），恢复行为依赖既有的 WAL/reclaim 重放路径
（由 Runbook A 的 `kill -9` 场景覆盖）。此处如实记录该边界，不作为本次验收的通过项。
