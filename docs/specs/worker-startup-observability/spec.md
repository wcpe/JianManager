# 功能规格：Worker 启动时长与分阶段进度可观测性

> 状态：草拟（待审核）　·　关联 PRD：FR-486（P1）　·　分支：feature/web-overhaul
>
> **重要前置**：本 spec 的 §6 待定 1 指出，FR-486 的四项范围中**第③项可能已由 FR-484 + FR-496 完成**，动因（1.2GB 状态文件）的根因已被消除。因此第③项是否仍需做，要先用 §5.1 的测量口径取数判定，**不预设结论**。

## 1. 背景与目标

2026-09-28 生产实测：Worker 重启后 **8m39s 才注册上线**（19:31:35 启动 → 19:40:14 注册成功）。此期间：

- **主控台完全看不到该节点**（节点列表里没有它，因为 CP 只在注册成功后才建/更新记录）；
- 实例健康巡检不运行；
- 且**加载全程零进度日志**——平台对自己的启动过程同样无观测。

目标：让「Worker 从进程启动到可服务」这段黑盒变得可观测——既能定位慢在哪一段，也能在主控台上看到「它正在启动、卡在哪一步」。

属于阶段：**P1**（可观测性缺陷，生产已造成误判）。

## 2. 需求（要什么）

### 范围内

1. **启动分阶段计时与日志**：把启动链路切分为可命名的阶段，每阶段结束打一条含 `elapsed_ms` 的日志；启动完成时打一条汇总（总耗时 + 各阶段耗时 + 最慢阶段）。
2. **进度可见（注册前）**：在主控台能观察到「某节点正在启动，当前处于 X 阶段」——这是 PRD 范围②，也是本 FR **唯一需要新增跨进程通道**的部分（见 §6 待定 2 的三种方案）。
3. **大状态文件加载优化**：**待测量判定**——若复测显示加载仍显著拖慢注册，则做；若已被 FR-484/496 解决，则本项**不做**，并在 PRD 里记为「已由前置 FR 消除」。
4. **状态超阈值的启动前告警**：启动时若状态数据规模超过阈值，打 WARN 并给出可操作的处置建议（而非等它拖慢启动后才由人发现）。

### 不做（范围外）

- 不改 CP 侧「节点必须先注册才可见」的基本语义（除 §6 待定 2 选定方案所需的最小改动）。
- 不做 Worker 启动的并行化/预热（那是性能改造，本 FR 只做可观测；若 §5.1 判定需要性能改造，另立 FR）。
- 不改 ingest 的数据格式与存储后端（FR-484/496 已定）。

## 3. 设计（怎么做）

### 3.1 阶段划分（事实依据：`apps/worker/main.go`）

按现有启动顺序切分（行号为当前代码位置，实现时以实际为准）：

| # | 阶段名 | 代码位置 | 说明 |
|---|---|---|---|
| 1 | `config` | `main.go:381` | 配置加载 + 日志装配 |
| 2 | `dataroot` | `main.go:477` | 数据根初始化 |
| 3 | `identity` | `main.go:487` | 本地节点身份读取 |
| 4 | `process_recover` | `main.go:586` | daemon 实例恢复 |
| 5 | `ingest_index_open` | `main.go:1078` 内 `openIndex()` | 索引打开 + 旧格式迁移 |
| 6 | `ingest_state_load` | `main.go:1078` 内 `load()` | **状态载入（历史瓶颈所在）** |
| 7 | `register` | `main.go:1406` | 含退避重试，**必须与阶段 6 分开计时**（见 §5.1） |
| 8 | `heartbeat` | `main.go:1527` | 心跳启动，此后节点可服务 |

实现形态：一个轻量 `startup.Tracker`（新包 `internal/worker/startup`），提供 `Begin(name)` / `Done(name)` / `Summary()`，内部只累积 `map[string]time.Duration` + 总起点。**零外部依赖、无锁竞争**（启动期单 goroutine 串行调用）。

> 不引入第三方 tracing：启动期还没有 CP 上下文，OTel 导出会把「启动可观测」绑到「可观测后端可用」，反而在最需要时失效。

### 3.2 阶段日志（范围内①）

每阶段结束：`slog.Info("启动阶段完成", "phase", name, "elapsed_ms", ms)`。
启动完成：`slog.Info("启动完成", "total_ms", ms, "slowest_phase", name, "phases", ...)`。
**默认开启**（不再藏 `JIANMANAGER_STAGE_TIMING=1` 后面——运行期那套开关是给高频采集轮用的，启动期只跑一次，没有噪声成本）。

### 3.3 注册前进度（范围内②，方案待定）

三种候选，**待你拍板**（详见 §6 待定 2）：

- **方案 A（推荐）**：新增 `StartupProgress` unary RPC。Worker 在阶段切换时尝试上报（CP 不可达就静默丢弃，不阻塞启动）。CP 按 `node_secret` 或一次性 `enroll_token` 鉴权，把进度落到独立的 `node_startup_progress` 表（node_uuid、phase、started_at、updated_at、done）。节点列表 API 对「有进度但未注册」的节点返回「启动中 · 阶段名」。
  - 优点：不动 `Register` 语义、不改变就绪判定；上报失败不影响启动。
  - 代价：新增一个 RPC 与一张表。
- **方案 B**：扩展 `RegisterRequest` 带「启动阶段快照」，注册成功后一次性回填。
  - 优点：零新增 RPC。
  - **致命缺陷**：注册发生在加载**之后**（`main.go:1406` > `:1078`），所以这条通道**恰恰无法覆盖最需要观测的 8 分钟**。除非先改启动顺序——那属性能/结构改造，超出本 FR。
- **方案 C**：调整启动顺序为「先注册，再加载」，加载进度随现有心跳上行。
  - 优点：复用心跳，零新增 RPC；CP 立刻能看到节点。
  - **风险高**：注册后 CP 就可能向该节点派发任务/实例操作，而加载未完成时它并不真正就绪。需要额外的「未就绪」门禁（CP 侧按进度拦截派发），改动面远大于可观测本身。

### 3.4 超阈告警（范围内④）

启动时统计状态规模（索引文件大小 + 事件段总量），超过阈值打 WARN：
`"状态数据规模偏大，启动可能变慢"` + `size_mb` / `threshold_mb` / `建议`（如触发归档裁剪）。
阈值来自配置 `startup.state_warn_mb`（默认值待测量后确定，见 §6 待定 3）。

### 3.5 CP 侧展示

节点列表新增「启动中」展示位（当前 `model.NodeStatus` 只有 `offline/online/starting`，`starting` 是 CP 建记录时的初始态，**不是** Worker 加载进度）。本 FR 若采纳方案 A，则以 `node_startup_progress` 表为准渲染「启动中 · 阶段 6/8」，而不复用 `status=starting`（避免两种含义混用）。

## 5. 验收标准

### 5.1 测量口径（先于实现，且必须先经你确认）

**测什么**：`进程启动 → Register RPC 成功返回` 的墙钟时长，并**拆成** `加载` 与 `注册` 两段。

**怎么测**（关键：避免把「注册重试退避」误算进「加载耗时」）：

1. **CP 必须真实在线且可达**（不能指向不存在的端口——否则测到的是指数退避）。用独立端口的验收 CP。
2. Worker 首次注册即成功，因此本测法只覆盖**稳态重启**场景；若需测「CP 不可达」，**另做一组**并单独标注，不混入加载耗时。
3. 以 Worker 日志时间为准：`Worker Node 启动`（起点）→ `ingest_state_load` 结束 → `注册成功`（终点）。取三次运行的中位数。
4. **至少两个规模点位**：① 默认空数据根（下界）；② 用脚本注入至配置上限的索引/事件段（上界）。规模与耗时一并记录，供外推。
5. 结论口径：若「加载」段在上界规模下仍 < 2s，则判定范围③**无需实施**，在 PRD 记为「已由 FR-484/496 消除」；若 ≥ 2s 或随规模显著增长，则范围③保留并据此定优化目标。

### 5.2 功能验收

1. 启动日志按 §3.1 八个阶段各打一条含 `elapsed_ms` 的记录；启动完成有一条汇总，含总耗时与最慢阶段（自动化用例断言日志字段存在与阶段名集合完整）。
2. 阶段耗时求和与总耗时的差 < 5%（用例断言，防「只计了想计的段」）。
3. 超阈时打 WARN 且含 `size_mb` / `threshold_mb`；未超阈时不打（两个用例）。
4. （若采纳方案 A）CP 在 Worker **注册之前**即可查到该节点的启动阶段；Worker 在 CP 不可达时**不因上报失败而阻塞或退出**（用例模拟 CP 不可达，断言启动总时长不显著增加）。
5. （若采纳方案 A）主控台节点列表出现「启动中 · 阶段名」，注册完成后转为正常在线态（真浏览器复验）。
6. 既有测试全绿；`make proto` 无未提交差异。

> 第 4/5 条属**真实环境维度**：需起真实 CP + Worker 复验，单元测试不替代。

## 6. 风险 / 待定

1. **【已测量·结论：范围③ 需要做】** 原先怀疑「③ 已由 FR-484/496 解决」，实测**推翻了该怀疑**：

   | 索引行数 | `Load()` 耗时 | 每 1k 行 |
   |---|---|---|
   | 1,020 | 5.4 ms | 5.4 ms |
   | 10,200 | 49.5 ms | 5.0 ms |
   | 50,200 | 267 ms | 5.3 ms |
   | 100,400 | **441 ms** | 4.4 ms |

   夹具见 `internal/worker/logs/ingest/stateindex/load_scaling_bench_fr486_test.go`，跑法：
   `go test ./internal/worker/logs/ingest/stateindex/ -run '^$' -bench BenchmarkLoadScaling -benchtime 1x`。

   **原因（代码级）**：`Store.load()` 对**每张表**做 `SELECT ... ORDER BY`（`store.go:823`），是**全表扫描 + 逐行解码**；`persist` 那套「只写变更源、根表 O(源数)」的增量优化**不覆盖 load 路径**。所以加载成本随总行数线性增长。

   **外推**：`plan.go` 注释记录生产 307MB 副本有 **746,884 行**，按上表 ~4.4–5.3 ms/1k 行推算，冷加载约 **3.3–4.0 s**；旧事故的 1.2GB 规模更大。这解释了「8m39s 才注册」中相当一部分（其余可能来自旧格式 `json.Unmarshal`，那部分确已被 FR-496 消除）。

   **真机基线（下界）**：空数据根下 `起点 → 注册成功` = **118 ms**，其中 ingest 段 ≈ 0 ms。说明正常规模无问题，问题只在**大索引**。

   → 因此范围③**保留**，优化目标定为：**100k 行下 `Load()` 从 441 ms 降到 ≤100 ms**（约 4×），并保证 746k 行 ≤1 s。

2. **【需拍板】注册前上报通道选哪个**（§3.3 A/B/C）。我的推荐是 **A**，理由：B 在时间上覆盖不到瓶颈段（注册晚于加载），C 有派发未就绪节点的风险。但这是架构取舍，需你确认；若选 C，本 FR 范围会显著变大（需加就绪门禁）。

3. **【需拍板】超阈默认值**：`startup.state_warn_mb` 默认值需等 §5.1 的规模-耗时曲线出来才能定。暂不预设。

4. **风险**：阶段计时只测到「我们切出的边界」。若真实耗时藏在某个阶段**内部**（例如 `load()` 里的恢复环节），八段划分会显得「每段都不慢但总时很长」。缓解：`ingest_state_load` 内部若已有细分点（`runStartupRecovery` 等），再拆子阶段；实现时先测量、按实测热点决定拆分粒度，不预先过度分段。

5. **风险**：默认开启阶段日志会改变现有启动日志形态，若有外部日志告警规则依赖既有行，需同步核对。

6. **【提示】与既有运行期计时的区别**：`recordRoundStage` / `采样批次阶段耗时`（`runtime.go:3776-3797`，受 `JIANMANAGER_STAGE_TIMING=1` 控制）是**采集轮内**计时，与本 FR 的**启动期**计时无关。实现时不要误改或复用那套开关。
