# 功能规格：日志采集开关组与 gz 导入缺陷修复（FR-504）

> 状态：**计划**（尚未实现）
> 关联 PRD：**FR-504**　·　依赖：FR-503（配置下发链路）、FR-502（规则引擎）
> 关联：FR-474（采集底座）、FR-501（日志成本治理——本项为其「gz 文件吸存未做」缺口的收口）
> 动因：2026-10-15 需求（开关可配）+ 同日实测发现的生产缺陷（814 个 gz 零导入）

本规格不得重新定义 FR-473 Shared Contracts；字段、状态与覆盖语义以
`docs/specs/worker-log-platform-contract/spec.md` 为准。

---

## 1. 背景与目标

本项含**两部分**：① 新增两个采集开关（gz 导入 / 实时采集）；② 修复 gz 零导入缺陷。

### 1.1 开关需求

- **gz 导入**：手动触发 + 定时扫描（当前 `log_ingest.archive_scan_interval` 为空 = 关闭）
- **实时采集**：应急开关——可临时停采而不停服（排障/降载），恢复后从断点续采不丢位置

### 1.2 缺陷（关键）

**现象**（worker.yml 注释记录，2026-10-15 复核）：生产 **164 个源中 151 个含 814 个 gz 待导入**，
而 catalog 中 **gzip 段记录为 0 条（从未导入）**。

**关键判据 —— 这是实现缺陷，不是功能缺失**：

`docs/specs/worker-log-acquisition/spec.md` 第 58/60 行**早已声明**：

> 第 58 行：`latest.log → 轮转 → .gz` 是**同一逻辑源的连续分段**，`.gz` 接管前必须登记前段结束位置
> 第 60 行：FILE_PRIMARY 常驻循环**自动发现同目录 `.gz`**（可用 `archive_glob` 收窄）

⇒ 架构设计**支持 gz 自动导入**，实现**未跑通**。

**疑似根因**（worker.yml 注释给出，待验证）：

```go
// runtime.go:2932 ImportArchivesNow 使用无界锁
m.cycleMu.Lock()
```

而同文件 `ResolveCoveredGapsForSource` **早已改用 `acquireCycleMuBounded`**（有界获取）。

即：`ImportArchivesNow` 用**无界** `cycleMu.Lock()`，在采集吞吐饱和期被饿死 ⇒ gz 导入永不执行。

> **注意**：worker.yml 注释称此为「历史」问题（"# 2026-10-10 关闭（用户裁定）"），
> 但用户已确认「**直接清理，本次一并查清并修复**」——故本项包含根因验证与修复。

**目标**：
1. 两个开关可配（经 FR-503 的配置链路，或 `worker.yml` 基线）
2. gz 导入缺陷**有根因结论 + 可转红回归 + 生产验证**

**非目标**（范围外）：
- 不改动 gz 解压算法本身（`acquire.NewArchiveImporter` / `ImportGzip`）
- 不做分级验证/吸存策略（属 FR-501 的「gz 文件吸存」范围，本项只保证**能导入**）

## 2. 需求（要什么）

### 2.1 开关

| 开关 | 行为 | 默认 |
|---|---|---|
| `gz_import_enabled` | 是否允许 gz 导入（关 = 连常驻循环的自动发现也停，只留手动入口） | `false`（保守） |
| `gz_scan_interval` | 定时扫描周期（空 = 关闭）；接通既有 `archive_scan_interval` | 空 |
| `realtime_tail` | 实时采集（关 = 停 tail 不采集新日志，服务照常运行） | `true` |

**语义要点**：
- `gz_import_enabled=false` 时**手动导入入口仍可用**（应急补历史），仅停自动路径
- `realtime_tail=false` 是**应急停采**：不影响实例进程、不影响已存数据、恢复后从断点续采
- 两个开关都经 FR-503 的配置链路，支持平台默认 + Worker 覆盖

### 2.2 gz 缺陷修复

1. 验证根因：`ImportArchivesNow` 是否真被无界锁饿死
2. 修复：改为有界获取（对齐 `acquireCycleMuBounded` 模式）
3. 可转红回归：**逐字还原旧实现，实测转红**（锁饿死场景）
4. 生产验证：以 login-01 的 80 个 gz 做真机导入

## 3. 设计（怎么做）

### 3.1 开关接线

**gz 导入开关**：
- 现有 `RunArchiveScan(interval)`（`ingest/runtime.go:3330`）：`interval <= 0` 即关闭 ⇒ 已具备关闭语义
- 新增：`gz_import_enabled` 控制**常驻采集循环内的自动发现**（spec 第 60 行所述行为）
  ——需在 `discoverSourceArchives`（`runtime.go:3667`）的调用点加判据
- 手动入口 `ImportArchivesNow(storageNamespace, operator)`（`runtime.go:3230`）**不受开关影响**（应急可用）

**实时采集开关**：
- 在采集轮（cycle）入口加判据：关闭时**跳过 Poll/tail**，但保持
  - 账本与 WAL 状态不变（可恢复）
  - 实例日志文件不被触碰（只停读，不移动/不截断）
  - 心跳与实例管理照常
- 恢复时从 `cursor` 断点续采（`FileTailer` 已维护 cursor，无需额外逻辑）

### 3.2 gz 缺陷修复

**调查步骤**（先证后修）：
1. 定位 `ImportArchivesNow`（`runtime.go:3230`）的锁获取路径
2. 对比 `ResolveCoveredGapsForSource` 的 `acquireCycleMuBounded` 实现
3. 用夹具复现：制造采集吞吐饱和，观察 `ImportArchivesNow` 是否永不进入
4. 确认后改为有界获取（超时返回明确错误，而非无限等待）

**可转红回归**：构造「采集轮长期持锁 + 调用 ImportArchivesNow」场景，
断言修复前超时失败、修复后成功。

**注意**：修复需保证**不破坏既有语义**——`ImportArchivesNow` 的
「扫描数/导入数」返回值、gRPC 入口的 operator 校验、以及 spec 第 58 行的
「`.gz` 接管前必须登记前段结束位置」约束，全部逐字不变。

### 3.3 与 FR-501 的边界

FR-501 的 PRD 行写「**gz 文件吸存**未做」，本项与之的关系：

| | FR-501 | FR-504（本项） |
|---|---|---|
| 目标 | gz 的**分级验证 / 吸存策略 / 成本治理** | gz**能被导入**（基础能力）+ 开关 |
| 边界 | 保留/分层/搬运策略 | 路径发现 + 开关 + 锁缺陷 |

⇒ 本项**不重复** FR-501 的策略工作，只保证导入链路可用；FR-501 的策略建立在「能导入」之上。

## 6. 风险 / 待定

- **锁修复的影响面**：`cycleMu` 是采集核心锁，改动需**逐字对照**既有语义（锁序、持有时长、与 `registerMu` 的关系见 FR-499）。**必须**跑 `-race` 与 logs 全量测试。
- **814 个 gz 的实际可导入性待验**：部分 gz 可能因已被轮转清理、或与 live 段位置冲突而不可导入。验收时应给出**逐源统计**，而非笼统的「全部成功」。
- **gz 导入的性能影响**：一次性导入 814 个 gz 可能造成采集侧压力；建议**限速或分批**（可复用 FR-501 的 `sampling` 预算机制，或加导入速率上限）。此项需在设计时明确。
- **`realtime_tail=false` 的语义易被误解**：需在 UI 明确标注为「**应急停采，非常规操作**」，并提示停采期间的日志将不被采集（写入 VL 的缺口）。
- **worker.yml 注释称此问题为「历史」**：需确认当前生产是否仍复现（2026-10-15 实测 catalog 中 gzip 段 0 条 ⇒ **仍复现**），避免误判为已修复。
