## 1. 背景与目标

助手有了运行时、工具、上下文和聊天界面之后，用户仍要「先点开一个入口」才能用。FR-520 把它变成**首页本身**：进入控制台第一屏就是问候语、提问框和建议问题，附一圈有界摘要；同时**不摧毁**已经打磨完成的经典仪表盘。

难点不在排版，在三条：

1. **两种模式都必须是「真」首页**，不能一个把另一个塞进页内——否则两套查询会同时挂载，首页直接多出十来个请求。
2. **经典模式不能被重做**。它已实现且有用户在用，改造半径必须限制在「加一层路由分支」。
3. **摘要必须按权限有界取数**。首页是每个用户都会打开的第一屏，把无收敛的接口搬上来等于放大既有缺口。

范围内：`/` 的默认 AI 模式、显式经典模式的 URL 契约与双向切换、AI 首页布局与摘要区、按权限的取数分支、宽窄屏与明暗适配、虚拟化/千级数据的渲染边界。

范围外：聊天运行时与工具（FR-515/516）、页面上下文采集（FR-518）、聊天组件本身（FR-519）、经典首页既有区块的任何重做、新指标或新聚合接口。

## 2. 现状核实（只读结论）

- **`/` 是整页替换式挂载，没有模式概念**：`<Route index element={<OverviewPage />} />`
  （[Workspace.tsx](../../../apps/control-plane-web/src/components/console/Workspace.tsx#L153)），
  `OverviewPage` 由 `lazy(ROUTE_CHUNKS['/'])` 载入（同文件 L14），
  `ROUTE_CHUNKS['/'] = () => import('@/pages/OverviewPage')`
  （[route-chunks.ts](../../../apps/control-plane-web/src/lib/shared/route-chunks.ts#L25)）。
  因此**模式切换加在路由层**是唯一不产生额外挂载的改法。
- **`ROUTE_CHUNKS` 是路由表与预取的唯一真源**（该文件头注释，FR-502 阶段 6）：`Workspace.tsx` 的
  `lazy()` 与预取器都从这里取加载器，任何新页面都必须登记进这张表，不得另写 `import()`。
- **经典首页的容器在 `pages/OverviewPage.tsx`，视图在 `components/views/overview/OverviewPageView.tsx`**。
  容器只做取数、权限判定与两处受控状态（`range` 时间窗、`activeGauge` 归因 Tooltip），
  仪表盘/聚合卡/趋势图/密集实例表交共享视图。**这层分工不要打破**。
- **经典首页实际发起的查询（实测，勿凭印象）**：
  `useNodes()` L34、`useInstanceSearch(...)` L43（异常卡：`status:'CRASHED', page:1, pageSize:5, sort:'name', order:'asc'`，服务端过滤取前 5）、

  AI 首页**不要**把它加回来。
- **三条候选摘要的权限收敛程度并不齐平**（2026-10-23 复核）：
  `/tasks` 有用户归属收敛（`service/task.go`）；`/instances/search` 按实例权限收敛；

- **无 AI 首页、无模式开关、无首页相关 store**：本 FR 从零新增，不改造既有 store。

## 3. 冻结的共同选择

| 决策 | 取值 | 理由 |
|---|---|---|
| 模式判据 | `/` = AI 模式；`/?home=classic` = 经典模式 | 显式 URL 才能深链、刷新不丢；默认 AI 符合「首页即助手」的目标 |
| 挂载方式 | **路由层分支**，两棵树互不嵌套 | 查询随分支挂载；父组件无条件调两套 hook 会让两套查询都跑 |
| 默认值 | 无模型时**仍进 AI 模式**，页内引导去配置；不因缺模型自动跳经典 | 「无模型也可切经典」是**可切**，不是**自动切**；自动跳转会让管理员误以为首页坏了 |
| 模式记忆 | **记住上次模式**，存前端 `localStorage`（键 `console.homeMode`），**可重置** | 2026-10-23 用户决定。存前端即可，不必进服务端配置；重置入口保证「选错了能回去」 |
| 经典模式 | **原样保留**，不加新区块、不改既有查询口径 | 它已完成且有用户在用；改造半径限于路由分支 |
| AI 首页摘要范围 | 只做「需要关注 / 近期任务 / 集群水位」三类，全部有界 | 首页不是第二仪表盘 |
| 取数权限 | 每个区块各自按权限决定**是否挂载**（`enabled`），不做「先取再前端过滤」 | 前端过滤挡不住请求，等于把数据发给了无权的人 |
| 告警摘要 | 受限告警读落地前，**仅平台管理员挂载** | 见 §2：`/alerts/events` 无 scope 收敛，不能给普通用户 |
| 上下文 | 首页输入器默认不带页面上下文（首页无实体）；可手动选实例 | 见 FR-518 §5.3 |

## 4. 路由与切换

### 4.1 URL 契约与优先级

| URL | 渲染 | 说明 |
|---|---|---|
| `/` | 按**记忆的模式**渲染；无记忆时 `AssistantHome` | 见下方优先级 |
| `/?home=classic` | `OverviewPage` | 显式指定，优先级最高 |
| `/?home=assistant` | `AssistantHome` | 显式指定 AI（与无参数区分：无参数才吃记忆） |
| `/xxx?home=classic` | 其它页，`home` 参数**被忽略** | 不要把 `home` 变成全局开关 |

**优先级（冻结，逐级下降）**：

```text
显式 ?home= 参数  >  前端记忆  >  默认（AI 模式）
```

- **`?home=` 只对本次渲染生效，不写记忆**。理由：用户点一条经典深链（比如从文档/告警链接进来），
  不该因此永久改变他下次打开首页的模式。记忆**只在用户主动点切换入口时**更新。
- 无 `?home=` 时读记忆；记忆缺失或值非法（非 `classic`/`assistant`）→ 回落默认 AI 模式，
  并把非法值当作缺失处理（不报错、不写回）。
- 切换时**保留其它无关合法查询参数**，只增删 `home`。
- 非 `classic`/`assistant` 的其它 `home` 取值（如 `?home=foo`）按**无参数**处理，即走记忆→默认的链路；不报错页。
- 深链 `/?home=classic` 刷新后仍在经典模式；且**取消记忆后**，直接访问 `/` 应回到 AI 模式（见 §4.4 重置）。

### 4.2 模式记忆（前端）

| 项 | 约定 |
|---|---|
| 存储位置 | `localStorage`，键 `console.homeMode`（与 `stores/console.ts` 既有偏好键同前缀风格） |
| 取值 | `'classic'` / `'assistant'`；**不写第三个值**，偏好即为默认时不写键（等价于缺失） |
| 写入时机 | **仅**用户点击 §4.3 的切换入口时写入 |
| 读取守卫 | 按 `stores/console.ts` 的既有惯例：`typeof localStorage === 'undefined'` 时回落默认；解析失败/非法值一律回落默认，不抛错 |
| 跨用户 | **不按 `userId` 分区**。模式是界面偏好而非业务数据，不含身份信息；同浏览器换用户时沿用同一偏好是可接受的（若按用户分区，反而会让新用户每次都被重置到他没选过的默认） |
| 登出 | **不清除**。登出清理的是会话/草稿/凭据（FR-519），界面偏好属于设备级设置 |
| 重置 | 提供显式重置入口，清除该键（`persist(key, null)` 语义，即 `removeItem`），重置后立即回到默认 AI 模式 |

### 4.3 路由层实现

```text
<Route index element={<HomeRoute />} />
```

`HomeRoute` 只做一件事：**按 §4.1 的优先级**决定渲染哪棵树——读 `searchParams.get('home')`，
缺失时读 `localStorage` 的 `console.homeMode`（§4.2），仍缺失则默认 AI 模式。
**它自己不得调用任何数据 hook**——这是「查询随分支挂载」的结构保证。
（页内条件渲染也能做到互斥，前提是两棵子树各自持有 hooks；选路由层是为了让约束由结构保证，而不是靠每个页面自觉。）

⚠️ **读记忆不得造成二次渲染抖动**：`HomeRoute` 首次渲染时若「先渲染默认 AI、再在 effect 里读到记忆切成经典」，
用户会看到一次闪回，且**两棵树的 chunk 都可能被拉下来**（正好破掉本节的目的）。
因此记忆必须在**首次渲染前同步读取**（`useState` 的惰性初始化或模块级 `loadHomeMode()` 均可，
按 `stores/console.ts` 的同步 `loadString` 惯例），不要放进 `useEffect`。

两棵树各自 `lazy` 分包，切到经典模式不该把 AI 首页的 chunk 也拉下来。

**分包必须走 `ROUTE_CHUNKS` 这张表**，不要直接在 `Workspace.tsx` 里写 `import('@/pages/...')`：
`route-chunks.ts` 是「路由表与预取的唯一真源」，`Workspace.tsx` 的 `lazy()` 与预取器都从它取加载器；
若两处各写一份 `import()`，一旦漂移（改名、换目录）预取会静默下载另一个 chunk，白花流量且毫无效果
（该文件的头注释已明确记录这条教训，FR-502 阶段 6）。落地时：

- 新增一页 `AssistantHome`，**给它自己的 chunk 键**（如 `'/home/assistant'` 这类不对外路由的内部键，
  或按该表现有约定另加一个键），**不要覆盖** `ROUTE_CHUNKS['/']`——那是经典页的加载器，
  覆盖它会让预取与既有用例指向错误模块。`HomeRoute` 按 §4.1 优先级从表里取对应加载器。
- 若预取器按路径预热 `'/'`，需明确「预取哪一棵树」——**按记忆/URL 判定出的当前模式预热那一棵**，
  不要两棵都预取（否则等于把两棵树的下载成本都付了）。

### 4.4 切换入口与重置

| 位置 | 方向 | 形态 |
|---|---|---|
| AI 首页头部 | AI → 经典 | 显式文字/图标入口「经典视图」 |
| 经典首页头部 | 经典 → AI | 同位置镜像入口「AI 视图」 |

- 入口必须**双向**且位置对应，用户不会「进去出不来」。
- 点击切换入口时：**先写记忆（§4.2），再导航**。两者顺序不能反——先导航会让新页面按旧记忆再判一次，出现闪回。
- 不用模态确认：切模式不改数据，无副作用。
- 主题、圆角、微元素档位、焦点环沿用既有 token（shared-contracts §9 末条）。

**重置入口**（用户明确要求「可以重置」）：

- 位置：切换入口旁，以次级操作呈现（如 `DropdownMenuItem`「重置首页偏好」或切换按钮的小齿轮菜单），
  **不与切换入口本身同等视觉权重**——它是低频纠错操作，不是主操作。
- 行为：清除 `console.homeMode` 键 → 立即按默认（AI 模式）重新渲染；若当前 URL 带 `?home=`，
  则**先清除记忆再移除该参数**，否则会出现「点了重置但页面没变」的假成功。
- 反馈：一次轻量确认（toast 或按钮态变化，如「已重置为默认」），不需要二次确认弹窗。
- 重置**不影响**其它偏好（侧栏折叠、语言、工作区等各自独立的键）。

## 5. AI 首页布局

### 5.1 结构

桌面宽屏两栏，窄屏单栏：

```text
┌─────────────────────────────────────────┬──────────────────┐
│ 问候语（按时段）+ 角色化称呼             │ 需要关注（摘要）  │
│ 输入器（复用 FR-519 的 AssistantInput）  │ 近期任务          │
│ 建议问题（3~5 条，可点击直发）           │ 集群水位          │
│ 最近会话（继续上次）                     │ 模式切换入口      │
└─────────────────────────────────────────┴──────────────────┘
```

- **问候语**按时段变化（早/午/晚），纯文本，不做个性化推荐。
- **建议问题**按当前权限取：普通用户不提「集群健康墙」「平台 SLO」这类他看不到的东西。建议问题是**静态文案 + 传参**，不是模型生成（首页不该为了显示建议问题而发一次模型请求）。
- **最近会话**取 FR-515 的会话列表前 5 条，按 `updatedAt` 倒序；无会话时该区块不显示（不留空壳）。
- 窄屏（<768px）：单栏，顺序为 问候 → 输入 → 建议 → 需要关注（异常实例 + 告警）→ 近期任务 → 集群水位 → 最近会话。
  摘要区**不折叠成横向滚动**。
- **实施偏差（已定）**：「最近会话」实际放在**右栏末尾**，而上方示意图把它画在左栏。
  原因是两条要求在窄屏下冲突——窄屏两栏是上下堆叠（左栏整体在前），若把它留在左栏，
  它会跑到「需要关注/近期任务/集群水位」之前，违背本节明确要求的末端位置。
  §8 的硬性验收只有「窄屏顺序正确」，宽屏位置无验收项，故以窄屏顺序为准。
  e2e：`e2e/assistant-home-responsive.spec.ts`。

### 5.2 不做的三项（明确）

- **完整实例表**：已在 2026-10-23 从经典首页移除，`useInfiniteInstanceSearch` 不再被首页引用；AI 首页也不加回来。
- **资源趋势图 / 健康墙**：属经典模式的完整仪表盘能力，AI 首页不做。若需要集群水位，用 `/metrics/overview` 的 totals 概览，**不挂健康墙**。
- **第二套指标查询**：AI 首页不复用 `usePlayerTrend` / `useInstanceRanking` / `useSLO`。
  关于 `useMetricOverview`：**只取 totals 概览**（即 §6 的集群水位），**不画它的趋势图**——
  同一个 hook 的两种用法要分清，别因为「不画趋势图」就误以为整个 hook 都不该用。

## 6. 摘要区取数（按权限）

| 区块 | 数据来源 | 权限判据 | 空态 |
|---|---|---|---|
| 需要关注（异常实例） | `/instances/search?status=CRASHED`（前 5） | 既有实例读权限；无权限则不挂载 | 「当前没有异常实例」 |
| 需要关注（告警） | `/alerts/events?resolved=false&pageSize=5` | **仅平台管理员**（受限告警读落地后放开，见 §7） | 管理员：「无未解决告警」；非管理员：**整个告警区块不渲染** |
| 近期任务 | `/tasks?limit=5` | 既有任务读权限（服务端按用户归属收敛） | 「暂无进行中的任务」 |
| 集群水位 | `/metrics/overview` 的 totals（`range` 为**必填**参数，用固定默认如 `24h`，首页不提供时间窗切换） | 平台观测权限（`monitor.read` / `node.read` / 超管，复用 FR-432 判据） | 无权限则不挂载 |
| 最近会话 | FR-515 会话列表（前 5） | 会话所有者本人 | 无会话则不渲染 |

规则：

1. **每个区块独立挂载与独立失败**。一个摘要接口 500 不影响其它区块，也不影响输入器——首页的核心功能是「能直接提问」。
2. **不合并成一个大请求**。不新造「首页聚合接口」：那会把多个权限域混在一个响应里，权限判定被迫在服务端做并集，很难不出错。
3. **不新增轮询，但要处理既有 hook 自带的轮询**。首页摘要原则上进入时取一次；用户要看实时状态应去对应页面或问助手。
   ⚠️ **例外必须显式处理**：`useMetricOverview` 自带 `refetchInterval: 10_000`（每 10 秒，
   `apps/control-plane-web/src/api/metrics.ts` L238-L250），且 `range` 是**必填**查询参数；
   `usePlatformObservabilityOverview` 同样带 `refetchInterval: enabled ? 10_000 : false`（同文件 L294-L302）。
   若直接拿它们做集群水位，首页会静默变成每 10 秒轮询一次，与本条规则矛盾。落地二选一：
   (a) 首页侧包一层不走轮询的取数（如 `useQuery` 直调同一端点、不设 `refetchInterval`）；
   (b) 给这些 hook 增加可覆盖 `refetchInterval` 的选项，首页传 `false` 或更长间隔。
   **不允许**「就让它轮询吧」——首页是常开页，10 秒一次的全平台指标查询在多人同时在线时会明显抬高 CP 负载。
4. **区块内最多 5 条**，超出引导去对应页面（「查看全部」链到既有列表页，带上既有筛选参数）。

## 7. 前置任务：受限告警读路径

**这是本 FR 唯一的硬前置**，不做则「告警按权限有界取数」这条验收无法达成：

- 现状：`/alerts/events` 无 `UserAccess` 收敛（§2 已实证）。它服务的是「能读告警的人看全部告警」，在既有页面语境下是有意取舍。
- 本 FR 需要的是**一个新的、按调用者可见范围收敛的告警读路径**（或给现有端点加可选收敛模式，二选一，实施时定）。
- 在它落地前：**AI 首页的告警摘要只对平台管理员挂载**；普通用户不显示该区块。
- 禁止的三种「变通」：
  1. 前端取全部再过滤——请求已发出，数据已到浏览器。
  2. 用「普通用户看不到告警入口」代替——首页是新入口，不能继承旧页面的隐含假设。
  3. 在验收里把该项标为「部分通过」——要么有收敛，要么不挂载。

### 8.3 键盘顺序：原文已修订（2026-10-27 决策）

原文曾要求「Tab 顺序为 问候 → 输入 → 建议 → 摘要 → **切换入口**」，即切换入口在内容流末尾。
实际实现把它放在 `PageHeader` 的 `actions` 里（AssistantHomePage.tsx 第 161～184 行），
Tab 顺序上出现在内容区**之前**。

**决策：修订验收原文，不改实现。** 理由：
- 页头承载页面级操作是通行做法，切换首页模式正属页面级而非内容内操作；
- 原文那句更像把「内容流顺序」与「页面级操作」混在一起写，而非有意要求按钮沉底；
- 可访问性未受影响：切换入口可获得焦点、有可见尺寸。

已执行：
- §8 验收条目改写为「**内容区** Tab 顺序为 问候 → 输入 → 建议 → 摘要；切换入口属页面级操作，
  位于 `PageHeader`，不在内容流末尾」。
- E2E 相应断言两件事：①输入器可聚焦；②切换入口可聚焦且有可见尺寸。
  **不断言**切换入口在输入器之后——那是被明确弃用的旧要求。

  **旧深链（节点/实例/监控）：已修复并验证通过（2026-10-27 第五次尝试）**

前四次尝试都卡在「概览页零链接」，误以为是数据不够。第五次换思路后真相是**两个问题叠加**：

1. **那些链接默认不渲染**——它们在资源归因 Tooltip 里（「总 CPU / 总负载 / 总内存 资源归因」三个按钮），

2. **点开之后发现链接是坏的（真缺陷）**：`OverviewPageView` 生成 `/monitoring?instance=<uuid>`，

**修复（两处）**：

- `OverviewPageView` 三处下钻链接改指 `/monitor?node=` / `/monitor?instance=`（新路由本就支持这两个参数）；
- `Workspace.tsx` 新增 `RedirectKeepQuery`，三条旧路径重定向时**保留 query**——
  这样外部收藏夹、文档里的旧链接仍然有效，不会静默丢参数。

**实测（真实 CP + 真实 Worker + 真跑起来的实例）**：

- 用 `sleep 3600` 作为 startCommand 创建实例（`processType=direct`），Worker 真的 spawn 起来，
  `status=RUNNING`、`uptime` 递增；
- `/metrics/resource-attribution` 返回真实采集结果：
  `topInstances: [{instanceName:"metric-probe", rssBytes:933888, sampledAt:...}]`，`freshness: fresh`；
- 点开归因 Tooltip 后页面出现 `/monitor?instance=aafee525-...`、`/monitor?node=c2e4b683-...`；
- 点击后落在 `/monitor` 且 **`?instance=` 参数保留**，监控页标题显示该实例 uuid；
- 另一路验证：直接访问旧路径 `/monitoring?instance=...`，重定向后 query 同样保留。

**这条验收现在是可以勾的**——它验的就是「既有下钻链接跳转后行为不变」，而修复后的行为确实正确。

**环境清理**：测试库（含供应商凭据密文）已移出仓库到 `/tmp/jm-trash/`，未留在 `data/`；

  ### 8.8 真实模型与工具链（2026-10-27 本轮实测）

验收要求「真实模型提问一轮、真实内外部工具链各跑一次」。三条**分别**取证，来源不同，逐一注明：

| 事实 | 证据来源 | 边界 |
|---|---|---|
| 真实模型提问一轮 | **本轮**：真实 CP + `nustarapi` 的 `deepseek-v4.1-flash`（`discover-models` 发现），浏览器实测两轮对话，覆盖「真实鉴权头 → 受保护出站 → 真实 SSE → 落库 → 前端渲染」 | 用的是商业中转端点，非厂商直连 |
| 真实**内部**工具链跑一次 | **本轮**：同一真实模型，模型主动发起 `tool_call`（`system_search_tools` → `system_describe_tool` → `system_call_tool`），工具成功 **4 次 / 失败 0 次**，模型据工具结果答出「1」（= 库中实例数） | 空库时 `AgentPrincipal` 的 instance scope 为空，工具会被判「能力/scope 不足」——**这不是缺陷**，是 scope 由实例表推导的必然结果；造 1 条实例后即成功 |
| 真实**外部** MCP 工具链跑一次 | **本轮已补验**（2026-10-27）：自建本地 MCP 服务器（JSON-RPC over HTTP，`initialize`/`tools/list`/`tools/call`），配到 CP 后由**真实模型** `deepseek-v4.1-flash` 主动调用 `conn_fake_5fmcp_get_5fserver_5ftime`，工具返回 `2026-10-27T17:44:40`，模型据此作答。前序「发现 → 启用 → 模型调用 → 结果回灌」全通，终态 `completed` | 服务是**自建假 MCP**（真 HTTP + 真 JSON-RPC，但不是某个真实第三方服务）；FR-517 §8 另有对「规范级 MCP 服务器 + 真 SSE + Bearer + cursor 分页」的记录可并看 |

**本轮修掉一个真实缺陷（FR-544 的「已修」其实没接线）**：

外部工具名原先在 `assistant_mcp.go` 里**手拼点号**：`"conn." + slug + "." + name`。
而 OpenAI 规范要求 function name 匹配 `^[a-zA-Z0-9_-]{1,64}$`，点号不在其中——
真实商业模型会让**整个请求** 400（实测 deepseek 返回
`the tool name is invalid or duplicated`，一轮 run 直接 `failed`）。

`assistant_external_tools.go` 里其实**早就有**可逆编码函数 `assistantExternalToolName`
（`_` → `_5f`、其它非法字符 → `_XX`），但**没有任何调用点**——写了没接线，
于是「已修」只停留在函数层面。这正是本轮才暴露出来的原因：
之前的外部 MCP 验证搭配的是不校验工具名字符集的假模型。

修复后工具名变为 `conn_fake_5fmcp_get_5fserver_5ftime`，真实模型调用成功。

**本轮顺带发现的一个环境事实**（不是缺陷，避免下次误判）：助手工具的可见范围由
`AssistantPrincipalForOwner` 推导——平台管理员拿全部 caps，但 **instance scope 来自
`Pluck("id")` 查实例表**。空库 → scope 空 → 所有实例类工具都返回
「能力/scope 不足或操作被拒绝」。第一次实测时正是这个原因导致模型 8 轮耗尽
（`budget_exhausted`），造一条实例后立刻变为 `completed` 且工具全成功。

### 8.6 首页与浮窗的会话状态：发现是**两份独立状态**（2026-10-27）

  验收原文：「AI 首页与浮窗**共用同一份会话状态**：首页发起的会话能在浮窗里继续，反之亦然；
  不出现两份 store（FR-519 §3「外壳级单一 manager」）」。

  **代码证据**（不是推测）：

  - `pages/AssistantHomePage.tsx:59` → `const chat = useAssistantChat(true)`
  - `components/views/assistant/AssistantDock.tsx:49` → `const chat = useAssistantChat(open)`
  - `useAssistantChat` 内部全部是**组件级 `useState`**（`conversationId` / `streamingMessages` /
    `toolCalls` / `runError` …），没有模块级单例；`useSyncExternalStore` 只服务于**草稿**，
    不承载会话状态。

  两处独立调用 = 两份互不相干的状态，**与设计要求的「外壳级单一 manager」不符**。

  **为什么之前的 #154 却通过了**：那条验的是「首页发一条 → 打开浮窗能看到同一条」。
  浮窗会自己向 `/messages` 拉历史，所以**已落库**的消息两边一致，看起来像共享。
  真正的差别在**流式途中**：首页正在逐字输出的内容，浮窗那份状态里没有；
  反过来在浮窗发起、回首页也接不上。这正是本条要求「能继续」而 #154 没有覆盖的部分。

  **修复方向**（属架构改动，未擅自实施）：把 `useAssistantChat` 提升到外壳层
  （`ConsoleShell`/`Workspace`）调一次，经 Context 下发给首页与浮窗。
  影响面：首页在路由树里、浮窗在 Shell 层，两者不是父子，只能走 Context。
  风险：会话状态是「流式 + 取消 + 断线补读」的状态机，提升后需重新验证
  「关闭浮窗不中断 run」与「切会话不串消息」两条既有验收。

## 附录：浏览器端到端取证（2026-10-25）

`apps/control-plane-web/e2e/assistant-home-mode.spec.ts`（Playwright，devmock large=1200 实例）两条用例：

**每 2 秒重取**（FR-329），而首页是常开页——长期任务期间等于持续全平台任务查询，与本页另两处摘要
（异常实例、集群水位）刻意改为私有 key 不轮询的取舍相悖，也违背 spec §6「摘要不轮询」。
改为私有 key `['assistantHome','tasks']` 直调 `/tasks?limit=5`、不设 interval。
**实测对比**：修复前 30s 窗口该端点被请求 13～14 次；修复后 **0 次**。反向验证：回退修复后用例转红。

**测量方法上的一处修正（值得留给后来者）**：`/metrics/overview` 的 URL 与顶栏完全相同（顶栏也发
`?range=24h` 且自带 10s 轮询），所以「静置期该端点次数为 0」**永远不可能成立**。
改为**对照测量**：同一 30s 窗口在 `/`（有首页摘要）与 `/nodes`（无首页摘要）各测一次，
两者同幅承受顶栏轮询与噪声，**差值 ≈0** 才说明首页自己没加轮询（若接了 10s 轮询差值会到 ~3）。
