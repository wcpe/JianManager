## A. 阻塞实现（已全部定案）

### A1. 危险操作确认机制是否统一（FR-516 §10.1）

**现状事实**：`RequiresConfirm` 目前只是 `agentActionCatalog` 里的**目录标记**（[agent_capability.go](../../../internal/controlplane/service/agent_capability.go#L57) 注释写「FR-396：destructive 操作须服务端精确确认参数」），而各工具实际靠**参数名精确确认**兜底——`confirmBotName`、`confirmPath` 等（`mcp/tools_bot.go`、`mcp/tools_file.go`）。

**问题**：FR-516 引入统一票据机制后，平台会同时存在两套危险操作确认语义：

| 通道 | 当前机制 | FR-516 之后 |
|---|---|---|
| 聊天（用户委托） | — | 统一票据 + 10 分钟 TTL + 参数哈希绑定 |
| jmat MCP（Agent Token） | 参数名精确确认 | **不改**（按 shared-contracts §5.2「不顺手改旧策略」） |

**选项**：
- (a) 保持两套（当前设计）——改动最小，但同类操作有两种确认体验，审计口径也不一致
- (b) 一并迁移 jmat 通道到票据机制——统一，但要动既有 MCP 契约，风险与工作量都大
- (c) 先做 (a)，在 FR-516 spec 里预留 `source=jmat` 的票据扩展点，后续单独 FR 迁移

### A2. 「上游按用户隔离」如何证明（FR-517 §9.1）

**问题**：共享外部 MCP 连接能不能给普通用户用，取决于「上游是否按用户隔离」——当前设计只要管理员勾一个布尔。

**选项**：
- (a) 保持口头声明，不勾则**永久仅管理员可用**（当前设计，最保守）
- (b) 要求上游支持 per-user token 透传，连接级配置「凭据映射策略」
- (c) 暂不开放共享连接给普通用户，V1 只支持管理员自用

### A3. 会话保留策略（FR-515 §10.1）

`HISTORY_WINDOW = 200` 是占位值。聊天记录是**审计与追责材料**还是**临时会话**，直接决定表设计（是否需要分区、归档、按用户配额）。

- (a) 永久保留 + 用户手动删除
- (b) 按条数滚动清理（当前占位设计）
- (c) 按时间保留（如 90 天），到期归档

## 我的建议（供参考，非结论）

1. **A1 选 (c)**：先做聊天切片，但把票据抽象设计成可容纳 `source=jmat`，避免将来二次重构。这样既不动现有契约，也不把路堵死。
2. **A2 选 (c)**：V1 只让管理员用共享连接。理由是无法证明隔离的授权等于把管理员凭据借给普通用户，这是 ADR-105 明确要避免的。
3. **A3 选 (a)**：聊天记录涉及操作追责（模型建议 + 用户确认 + 工具执行），删了就无法回溯。存储成本可用按会话归档控制。
4. **B8 建议升级为 A**：不做基础 Markdown 会显著影响可用性，而实现成本不高（列表 + 粗体 + 行内代码 + 代码块四种即可）。
