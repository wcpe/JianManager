# 功能规格：平台全景观测总览与下钻

> 状态：开发中　·　关联 PRD：FR-402　·　优先级：P1　·　依赖：FR-400、FR-401

## 1. 背景与目标

现有首页分别拉取节点、实例、任务、告警和基础指标，缺少统一健康视图、资源解释和异常下钻。直接把所有节点和实例铺在首页会降低可读性，也会扩大数据量与权限暴露。

本 FR 为平台管理员提供一个总览读模型：显示聚合健康、资源、状态分布、告警、任务和 Bot 共享运行时；只展示有界 TopN/异常项，并把操作员带到既有节点或实例详情。

## 2. 需求（要什么）

### 范围内

1. 平台首页显示：节点/实例在线与异常计数、当前 CPU/负载/内存、FR-400 归因摘要、未解决告警、进行中/失败任务、Bot Worker 共享运行时聚合（RSS、真实 CPU、Bot 计数与事件循环 P95）。
2. 每个区域最多展示 5 条 TopN 或异常项；按 CPU/RSS、陈旧/离线、崩溃、未解决告警、失败任务等确定优先级。
3. 节点和实例项均可下钻到既有监控或实例详情；缺测、陈旧和离线状态明确可辨。
4. 可见页每 10 秒刷新，隐藏页暂停；不建立可持久化自定义仪表盘。

### 不做

- 不在首页添加全量节点、实例、日志或 Bot 明细表。
- 不新增写操作、告警规则、任务调度、进程控制或全局任意进程列表。
- 不重复实现 FR-400 Tooltip、FR-401 节点趋势或 FR-403 日志分流。

## 3. 设计（怎么做）

### 3.1 平台总览读模型

新增平台管理员端点 `GET /api/v1/observability/overview`，在 CP 服务层以有界查询聚合：

- `health`：节点数/在线/陈旧/离线、实例运行/崩溃/停止；
- `resources`：复用 `/metrics/overview` 口径与 FR-400 的受管资源摘要；
- `bots`：复用 FR-401 全平台聚合，明确为共享运行时；
- `alerts`、`tasks`：只取未解决或非终态的最近/最严重 5 条；
- `exceptions`：节点陈旧/离线、实例崩溃、资源 TopN 的稳定有界列表。

服务层必须避免每条 TopN 再查询数据库或远程 Worker（无 N+1、无 RPC）。所有资源数据来自已持久化当前值或时序读模型。端点只对平台管理员开放，普通成员继续使用既有受限首页内容。

跨节点 `bots.eventLoopP95Ms` 定义为可用节点 P95 的最大值，用于突出最差共享执行节点；它不是跨节点重新计算出的全局分位数。无可用节点时该值为 `null`，并通过 `unavailable` 说明原因。

### 3.2 首页布局与下钻

保留现有概览骨架，平台管理员追加“平台健康”“异常项”“Bot Worker（共享）”三个区域。每个条目使用链接到既有 `/monitor`、`/nodes/:id` 或 `/instances/:id`，不新增独立详情页面。加载失败显示局部错误，不阻止原有首页渲染。

## 4. 任务拆分

- [x] 为平台总览聚合、TopN 限制、异常排序、权限和无 N+1 写服务/路由红测。
- [x] 实现平台总览服务与 API，复用 FR-400/401 读模型。
- [x] 实现首页健康/异常/Bot 共享区块与下钻，补齐空态、陈旧态、i18n、可访问性测试。
- [x] 更新 API、ARCHITECTURE、PRD、CHANGELOG；多节点真机验收仍待用户确认。

## 5. 验收标准

1. 首页只显示聚合与每类最多 5 条 TopN/异常项，不出现全量实体表。
2. 节点/实例离线、陈旧、崩溃、告警和失败任务均可识别，并能下钻到对应既有页面。
3. Bot 区只展示 FR-401 的共享进程资源与聚合计数，持续显示非单 Bot 归因说明。
4. 总览端点不发起 Worker RPC，服务/路由测试证明无按条目 N+1 查询。
5. 仅平台管理员可访问全景 API/区块；普通成员既有首页和资源范围不被扩大。
6. 前端定时刷新与隐藏暂停行为通过测试；Go、前端及真 CP+多节点环境验收通过并由用户确认。

## 6. 风险 / 待定

- FR-400/401 未交付时不得用临时 RPC 或零值伪造概览数据。
- 资源汇总与受管 RSS 非守恒关系，需继续沿用 FR-400 的观察值说明。
