### durable outbox r4 校验预算（本地候选已实现，联合验收中）

固定 12 次按原始校验簇定格，沿用同 ctx/截止和原始 UTC 窗，不按后续 Poll 续期，也不因切成多个 12KiB query 子片就提前耗尽完整证据所需份额。子片只缩 ID 集合，仍逐字段核对 `_time/_msg/event_id/level/stream/canonical_content_hash` 并跨响应去重；probe 只决定何时做完整证据轮，不能充作 VerifiedRuns、ACK、发布或回收证据。语义 Err 保留其类别，不转换为 Pending/copies；未知 written 先 RO 确认原实际目标。

公共 runtime 测试 fixture 的六字段响应改用 RawMessage，保留原缺失/null/错误类型/UTF8与转义，非六字段路径保持原始行，按 payload SHA 缓存等价元信息；这是测试响应协议修正，不是新生产能力，也不改测试预算/断言/输入。当前新完整 Worker 1s/9 窗、Search 与正式 9×30min 尚待真实结果；旧 FAST 大于 250ms、精确样本为 0，不能标达标或最优。详见 [r4 契约](../worker-log-platform-contract/spec.md#durable-outbox-r4本地候选已实现联合验收中)。

## 1. 背景与目标

### 1.1 实测现象（FR-498 续）

跨源并发落地后，60 源 × 30 行/s 饱和夹具的单轮 91.2% 仍在 `deliver`，其中**投影校验
（verify）占 85.6%**：96 次投递 × 4 批 + 重试 = **605 次校验查询、单次 141 ms**；
同期 VL 写入仅 1.8%、WAL 0.05%、Worker 与 VL 的 CPU 都没打满 —— 纯等待型瓶颈。

这道校验是「**投递后确认可见**」的保证，且当晚确实抓到过缺陷（只按代次名过滤导致日界/重名问题
都是它发现的）。**本项不削弱该保证**：判定规则、选择器、时间窗、日夹取、三类错误文案、
退避与超时语义逐字不变，改的只是「**一次读多少、读几次、怎么并行**」。

### 1.2 目标

verify 占比 **≤40%**（或吞吐 **≥3.0k 行/s**）；失败检出能力**不下降**（注入少写/写错/多写仍必须
被检出，错误类别不变）；可转红回归 + 门禁全绿。

## 2. 141 ms 的成本定位（本地夹具 + 真 VL v1.52.0 + 计时探针）

**夹具**：真 VictoriaLogs（v1.52.0，`-memory.allowedBytes=536870912`）+ 60 源 × 30 行/s × 2760 s
时间轴 = **4 968 000 行 / 377 MB**（与生产 VL 同量级：生产 500 MB / 5.13 M 行 / 11 源）。
探针复刻 `verifyProjectionOnceAllowed` 的查询参数（同 selector、同 `| fields`、不传 limit），
分段计时：TTFB（首字节）、body（读取 + 逐行 `json.Unmarshal`）、行数、字节数。

| 查询窗口 | 返回行数 | 返回字节 | 总耗时 | TTFB | body | 其中 JSON 解析 |
|---|---|---|---|---|---|---|
| 17 s（≈500 行/片） | 510 | 176 KB | 9.4 ms | 6.2 ms | 3.2 ms | 1.6 ms |
| 70 s（≈2000 行/片） | 2 100 | 725 KB | 14.7 ms | 3.8 ms | 10.9 ms | 5.8 ms |
| 300 s | 9 000 | 3.10 MB | 49.3 ms | 3.5 ms | 45.7 ms | 24.3 ms |
| **900 s** | **27 000** | **9.31 MB** | **137.8 ms** | 3.5 ms | 134.3 ms | 71.3 ms |
| 1800 s（生产 p50 跨度 45 min） | 54 000 | 18.6 MB | 276.6 ms | 4.1 ms | 272.5 ms | 145.0 ms |
| 2760 s | 73 800 | 25.5 MB | 367.5 ms | 3.6 ms | 363.9 ms | 193.4 ms |

**逐项裁决（任务列出的五个嫌疑）**：

| # | 嫌疑 | 裁决 | 证据 |
|---|---|---|---|
| ① | 扫描量／排序 | **不是** | TTFB 恒 2.5–4.1 ms（VL 的 part 时间裁剪 + block bloom 跳过都很快）；不加 limit 时 VL 不排序 |
| ② | 分片窗口 | **主因** | 成本与**窗口内返回行数**线性：`total ≈ 行数 × 每行 ≈345 B ÷ 65–80 MB/s` |
| ③ | 重试退避（默认 5 min 窗口） | **不是（放大器）** | 成功路径零退避；只有判「不可见」才退避重试（本地夹具 3471 次查询 / 821 批 ≈ 4.2 次/批，即 4 片 + 少量重试） |
| ④ | 连接复用 | **不是** | 客户端为 `http.Client`（连接池复用）；跨查询无新建连接开销（TTFB 与 QPS 无关恒定） |
| ⑤ | 客户端解析 | **放大器 ×0.5** | `json.Unmarshal` 占 body 的 **50–65%**（9.31 MB 一档：134.3 ms 中 71.3 ms） |

**批 → 查询的放大关系（读码 + 生产日志 + 夹具）**：`insertBatchMaxEvents = 500` 同时被写批与
**校验分片**复用 → 2000 行/批 = **4 次查询**；每次查询的窗口是「本片事件的 [min−1s, max+1s]（夹日）」，
而**批内事件的时间与索引顺序并不一致**（多条流混合、时间戳跳变、跨日批次），于是各片窗口互相
包含——**每一片都会把整批读回一遍**，读回量 = **k × n**（k = 片数）。批内各片**串行**执行
（`for start := 0; …` 循环），同源内等待逐个叠加。
生产实测（`worker.out`，15:52 窗口）：同一 (generation, source) 的 444 条校验查询日志里
只有 378 个不同查询串（重复 9 次者成段出现），窗口跨度 p50 = 2724 s、p99 = 85 933 s ——
即「500 行一片跨 45 分钟～24 小时」，窗口内除本片外还有大量同批记录。

**结论**：141 ms ≈ **2.7 万行 / 9.3 MB 的传输 + 逐行解析**（TTFB 仅 3.5 ms）。优化方向因此是
**减少读回次数与体积**，而不是换存储、加索引或调超时。

### 2.1 但「1.42 s/批」的主体不是查询，而是等 VL 可见

真进程夹具打点（新实现的 `投影校验完成`）显示：单批 `queries=4`（1 次命中 + 3 次空手退避）、
`elapsedMs` p50 = **1411 ms**，而 3 次退避（200+400+800 ms = 1400 ms）占 **99.3%**；
数据已可见时的真实查询在 500 行档位只有 **9.4 ms**（§2 表）。

**「写入 → 可查询」延迟探针**（插入一批 500 行后
固定 20 ms 轮询同一条校验查询，20 次试验）：

| min | p25 | p50 | p75 | p90 | max |
|---|---|---|---|---|---|
| 1011 ms | 1017 ms | **1025 ms** | 1027 ms | 1029 ms | 1029 ms |

即该延迟**几乎恒定 ≈1.02 s**（VictoriaLogs 的内存缓冲落盘节拍），与批大小无关。
⇒ 退避序列 200/400/800/封顶 2s 的探测点是 0 / 0.2 / 0.6 / **1.4** s，**恰好在 1.0 s 附近没有探测点**，
每次批级校验都白等约 0.4 s。这就是 §3.6 的动机。

## 3. 设计

### 3.1 按事件时间分簇（`planVerifyChunks`）

- 整批事件按 `canonicalEventTime` **稳定排序**后，每 `verifyChunkEvents`（默认 **2000**，
  与写入批上限 500 解耦）条切一簇；
- 每簇仍用原窗口公式（簇内 min−1s / max+1s，夹在本源 UTC 日内）与完全相同的 selector；
- 排序后簇内跨度就是 min/max 决定的，**相邻簇的窗口不再互相包含**（最多在 ±1s 容差处相接），
  读回总量从 k×n 降到 ≈n；
- 分簇粒度字段化（`Manager.verifyChunkEvents`），测试与回归用真实限额路径驱动。

**为什么默认 2000**：与「单源单次 poll 的典型满批」一致（常见情形 1 次查询）；
VL 侧安全边界是「单查询结果集内存」——实测 2.7 万行 / 9.3 MB 返回无压力，而恢复期
`limit=747822` 会让 VL 返回 400（`cannot calculate [sort by (_time) desc limit …]`，2026-09-28 事故）。
本实现**不传 limit**，因此不会触发该路径；2000 只是「一次读多少」的调度上限。

### 3.2 同批内并发（`verifyChunkConcurrency`，默认 4）

单次校验的成本几乎全在「返回体传输 + 逐行 JSON 解析」，属可并行部分；跨源并发（`pollConcurrency`）
只重叠了源与源之间的等待。同批内各簇用固定并发度的工作池执行，**任一簇失败即取消其余簇**
（与串行实现「失败即返回」语义一致）。

### 3.3 错误选择与取消噪音（并发引入的新面，必须显式处理）

- **取消只在「明确根因」到手时发生**：仅当某簇返回**永久失败**或**判定类错误**（内容不一致 /
  多余或重复 / 事件集非法）时才取消其余簇；**超时类失败不取消**——它往往只说明「本批数据尚不可见」，
  而其余簇此刻可能正读到真正的根因（例如某一行内容不一致），取消会把那个结论一并抹掉。
  **2026-10-02 复审 P1-3 更正**：该策略此前并未真正生效——本簇到期唯一的错误文案
  `not fully visible before deadline` 曾被 `verifyErrorIsSemantic` 判成判定类，于是任一簇到期都会
  取消其余簇、把即将读到的真根因覆盖成 `aborted by batch cancellation`。现已把该文案移出判定名单
  （取消只由 `vlsup.IsPermanent` 与真正的判定类错误触发），回归
  `ingest.TestVerifyProjectionTimeoutChunkDoesNotMaskContentMismatch`（超时簇 + 内容不一致簇 →
  verdict 必须是内容不一致；把文案放回名单即红）。
  这一条是 `-race` 实测逼出来的：注入「写错一行」后，若超时也触发取消，最终错误会退化成
  `verification failed: context deadline exceeded`，根因不可见。
- **判定类错误优先**：由「同批其他簇失败后取消」引发的传输噪音（`context canceled`、
  被截断响应体的 `unexpected end of JSON input`）不得覆盖真正的根因——实现见
  `verifyErrorIsSemantic` 与最终错误选择（判定类优先，其次传输类）。
- **本簇结论只在自己超时时成立**：`verifyProjectionChunk` 区分「父 ctx 取消」（其他簇已拿到根因）
  与「本簇自身窗口到期」。父 ctx 取消时立即收手并返回 `verification aborted by batch cancellation`
  （不计入判定类错误）。
- **超时类错误不改写根因**：本簇窗口到期时，若 `lastErr` 只是**本簇自己超时**引发的传输类错误
  （`context deadline exceeded` / `canceled`），仍报「到期仍不可见」而不是「校验失败」——
  否则现场会把「数据没可见」误读成「查询失败」（`verifyErrorIsTimeoutLike`，同为 `-race` 实测暴露）。
- **取消即收手**：`verifyProjectionQuery` 的流式消费在每次 `Scan` 前检查 ctx，避免把被取消的
  半截响应体报成 JSON 解析错误。

### 3.4 观测面（新增打点，纯增量）

- 每批一条 `投影校验完成`：`events / chunks / concurrency / queries / rows / bytes / elapsedMs / err`；
- 单次查询耗时 ≥ `verifySlowQueryThreshold`（500 ms）时另打 `投影校验慢查询`（含 rows/bytes）。
- 旧实现只有「投影校验查询」（查询前）一条日志，141 ms 级的慢查询与读回量在现场完全不可见——
  这是 FR-498 定位耗时构成的主要困难之一。

### 3.5 退避上限：2 s → 500 ms（`defaultVerifyBackoffMax`）

依据 §2.1 的可见延迟实测（恒定 ≈1.02 s）：退避**起步与倍率不变**（保持指数退避语义），
只把封顶从 2 s 收到 **500 ms** —— 探测点变为 0 / 0.2 / 0.6 / **1.1** s，数据一可见即命中并返回，
不再白等那 0.4 s。

**为什么不是「固定 200 ms 轮询」**：2026-09-28 生产事故正是固定间隔轮询到 30 s 超时
（单源最多约 150 次查询，把 VL 与磁盘一起压垮）。本项保持指数退避：数据长期不可见时，
2 秒窗口内的查询次数是 5 次（`TestVerifyProjectionBacksOffWhileDataNotVisible` 断言 ≤6，实测 5），
远低于事故量级；且查询本身的成本已被 §3.1 分簇压到「每批 1 次」。

### 3.5a 判定类错误立即失败（失败**时机**变化，判定结论不变）

内容不一致 / 多余或重复 / 事件集非法属**确定性结论**：VL 里的行内容已经定型，退避重试不会改变它。
旧实现把它当普通失败继续退避到窗口结束（默认 5 min）才报出同一结论——纯浪费，且让现场多等一个窗口。
新实现**立即返回**，错误文案与「重试到窗口结束」路径**逐字一致**（前缀同为 `verification failed:`）。

- **判定不变**：仍然是失败，仍然报同一类别与同一 event_id；
- **时机变化**：从「窗口结束」提前到「观察到该结论的那一次查询」；
- **观测证据**：注入用例耗时由 `10.01 s`（等满窗口）降到 `0.00 s`（内部查询 3 次），
  且 `-race` 全包运行下不再因负载抖动而误报；
- **为什么安全**：判定对象是「刚写入的这批事件」，其他批用不同 `projection_generation` 被 selector
  排除，故这些结论不会被「另一批正在写入」这类并发过程暂时伪造。

### 3.6 等价性论证（**强度不变**，逐条对照）
| 维度 | 旧实现 | 新实现 | 等价性 |
|---|---|---|---|
| 完整性 | 每片 events 全部可见才通过（`len(seen) == len(want)`） | 每簇相同判定 | 同一判据，判定对象仍是**每个** canonical event_id |
| 内容一致性 | 返回行的 `canonical_content_hash / _time / _msg / level / stream` 逐字段与期望比对 | 逐字相同（两处分支：want 与 allowed） | 未改动一行 |
| 重复检测 | 同一查询内同一 event_id 出现两次 → `unexpected or duplicate` | 相同 | 未改动一行 |
| 多余检测 | 窗口内出现不属于 allowed 的行 → `unexpected or duplicate` | 相同 | 未改动一行；**可见行的并集相同**：旧实现各片窗口的并集 = 整批 [min−1s, max+1s]，新实现各簇窗口的并集同样是整批范围（按时间排序切分不改变并集） |
| 选择器 / 时间窗 / 日夹取 | selector 取**该片首条事件**的 source 标识；窗口夹在本源 UTC 日内 | 取**该簇首条**（排序后即该时间段最早的事件；批内 source 标识一致） | 逐字相同的公式；簇内首条与片内首条的 source 标识同源 |
| 失败语义 | 串行，首个失败即返回；退避 200 ms→2 s 封顶；4xx/认证立即永久失败；默认 5 min 窗口 | 并发，判定类错误优先返回；**判定类错误立即失败**；退避 200 ms→500 ms 封顶；其余逐字不变 | 错误**类别**与文案完全一致（回归逐条断言）；差别只在**失败时机**——旧实现把「内容不一致 / 多余或重复」当普通失败继续退避重试到窗口结束（默认 5 min）才报同一结论，新实现立即报出（见 §3.5a） |
| 最强的差异 | — | 合并后同一 event_id 若在同一簇查询内出现两次，会被判重复（旧实现分处两片时可能不检） | **新实现更强**，不是削弱 |

**没有变的红线**：投递后仍必须「逐条确认可见且内容一致」才 `publish`；`releaseRecovery`
的持久接收者仍是投影；任何 HTTP 2xx 仍不构成耐久证明。

## 4. 回归与转红（实测）

`internal/worker/logs/ingest/verify_chunking_test.go`（假 VL 复刻真实窗口语义：按窗口返回行、
可注入缺陷、记录查询次数/读回行数/并发峰值/窗口）：

| 用例 | 断言 | 转红方式（实测） |

### 7.1 结论先行：**PASS —— 堆不随轮次泄漏，只随 WAL 积压涨**

`TestSoakWindow60Sources`（60 源、真 VictoriaLogs v1.52.0、`DeferredDelivery: true`）
跑完 900 轮（2m24s，加速窗）：

```
堆前1/3 = 9.6 MiB   后1/3 = 14.3 MiB   比值 = 1.49          ← 裸堆看像泄漏
WAL前1/3 = 0.74 MiB 后1/3 = 1.31 MiB
单位积压堆成本：前 = 13.0 MiB/MiB  后 = 10.9 MiB/MiB  比值 = **0.84（在降）**
⇒ PASS
```

离线回归（180 个采样点）：

```
heap = 4.58 × WAL_MiB + 8.01      残差 std = 2.89 MiB（即 GC 噪声）
```

⇒ 堆增长 **100% 可由 WAL 积压解释**，且每字节积压的内存成本反而下降。**不是慢泄漏。**

### 7.2 两个夹具缺陷（都曾把夹具自己的行为误读成产品缺陷）

**缺陷一：从未启动后台环（`Manager.Start`）。**

`DeferredDelivery: true`（生产配置，`apps/worker/main.go:1226`）下，投递与回收**全在后台环里**：
`Start` 的 250ms ticker 驱动采集轮，`RunCapacityResumeLoop` 的 `drainScheduledReplay` 驱动
`DeliverPending` 与 reclaim。夹具只调 `m.pollOnce()` ⇒ **只采不投** ⇒ WAL 只进不出：

```
修前：轮 10  Heap=3.5 MiB   WAL=600 条/0.2 MiB   pos{delivery=0 reclaim=0}
      轮 590 Heap=73.4 MiB  WAL=35400 条/14.1 MiB pos{delivery=0 reclaim=0}
      ↑ WAL 条数 == 60 × 轮次，一条都没回收
修后：轮 10  pos{delivery=960 reclaim=960}   轮 890 pos{delivery=72116 reclaim=72116}
```

单源对照实验直接坐实：同一夹具里手工调一次 `DeliverPendingContext`，
带真 VL 时 `delivered=true → delivery=49 reclaim=49 WAL=0`；不带 VL 时
`delivered=false err="VictoriaLogs client is not ready"`。**投递与回收本身是好的。**

**缺陷二：测试观测钩子自己累积事件。**

`newTestManager` 挂的 `deliverWriteHook` 把每次投递的全部事件追加进 `deliveredBySource`
（给单轮用例 `durableEvents` 读回内容用）。长稳带它跑 = 60 源 × 900 轮 = 54000 个
`logtypes.Event` 被永久持有，round 300 实测已占 **3.85 MiB** 并线性上涨。
长稳窗现已把它换成空钩子。

### 7.3 判据重写：裸堆比值 → 分离三个量（两次修正的终态）

原判据「后 1/3 的堆 ≤ 前 1/3 的 1.5 倍」**必然误报**：WAL 是有界缓存，只要投递稍慢于写入，
积压就震荡上升、堆跟着涨，那是设计行为。

但同日再修一次：只换「单位积压成本」**也不行**——1 行/s/源 的低速窗里 WAL 积压只有
0.06–0.09 MiB，分母近乎噪声；而给分母加一个 floor 会让两边变成同一常数，
**比值退化成裸堆比值**（实测 floor=0.1 时两边都是 X/0.1，与裸堆完全相同），指标失去诊断价值。

⇒ 终态是将三个量**分开验**，各自在自己的量级上有意义：

| 判据 | 适用条件 | 破的读法 |
|---|---|---|
| ① 堆 后1/3 / 前1/3 ≤ 1.5 | 积压几乎不涨（低速窗）；积压明显在涨时放宽到 3.0 | 常驻增长 |
| ② 每 MiB 积压的堆成本不上升超 1.5 倍 | 仅两侧积压均 ≥ 0.3 MiB 时计算，否则报 `n/a` | 常驻增长 |
| ③ 积压不得撞字节跌顶（60 × 16 MiB） | 恒适用 | 投递长期跟不上（吞吐问题） |

### 8.4 gaps 1→3 的解释（非采集器缺陷）

2 次 gap 是本测试方法造成的：

1. 注入脚本用 `open(...,'a')` 追写真实 `latest.log`，而 MC 进程同时也在写同一文件，双写导致 inode 被替换
2. 另一次是 `cp -a` 覆盖同名文件

**非采集器丢数据**，正是 `RecordGap` 设计要捕捉的形态。
