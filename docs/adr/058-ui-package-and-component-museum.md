# ADR-058: 通用组件包与控件博物馆

- **日期**: 2026-07-05
- **状态**: accepted
- **关联**: FR-273、FR-267~272、ADR-057

## 上下文

高密度控制台重塑已经确认以 A 亮色高密度运维台为默认主题，并吸收 C 方块拓扑 Logo/Favicon 语言。继续推进 Shell、侧栏、顶栏和主要页面时，若仍让 `web/src/components` 同时承载通用控件与业务复合组件，组件风格、暗色模式和页面性能基线会难以稳定。

项目需要一个明确的前端组件包边界，以及一个可视化入口持续检查控件、状态、token 与主题效果。

## 决策

新增 `web/packages/ui` 作为 `@jianmanager/ui` 通用组件包，新增 `web/wiki` 作为控件博物馆。

第一阶段决策：

- `@jianmanager/ui` 只抽通用 UI、组件级 token、通用图表和无业务依赖辅助函数。
- 控制台壳层、业务弹窗、API 驱动面板、文件/配置浏览器等业务复合组件继续留在主应用。
- 主应用和 wiki 都从 `@jianmanager/ui` 消费控件，wiki 不复制组件实现。
- `@jianmanager/ui` 第一阶段采用源码 alias 方式接入，不改根目录 monorepo 结构。
- 旧 `web/src/components/ui` 与通用 chart 入口允许保留迁移期 re-export，交付后逐步清理。
- 不引入 Storybook 或新的第三方文档工具。

## 理由

- 通用组件包能让 A+C 视觉语言在页面重做过程中有稳定消费面。
- 控件博物馆比隐藏在业务页面中的状态更适合检查明暗主题、禁用、错误、空态与组合样式。
- 源码 alias 方案能在当前 Vite 前端内完成抽包，避免根目录工程形态变化扩大风险。
- 只抽无业务依赖组件，可以避免把 router、store、API 与权限逻辑污染到设计系统包。

## 后果

- 后续前端页面级改造应优先消费 `@jianmanager/ui`，避免继续新增散落的通用控件实现。
- `web/wiki` 成为通用控件视觉验收入口，组件新增或变更时应同步展示。
- 前端工具链会增加 `@jianmanager/ui` 与 wiki 的解析/构建配置，但不影响后端部署模型。
- `docs/API.md` 不需要因本 ADR 变化；本决策不新增后端接口。

## 替代方案

- **根目录改为完整 monorepo packages/apps**：边界更彻底，但会牵动根构建、脚本和部署，超出当前 FR 所需。放弃。
- **只在主应用内新增设计系统路由**：实现更少，但会继续和业务路由、鉴权、全局状态耦合，不适合作为独立控件博物馆。放弃。
- **引入 Storybook**：生态成熟，但会新增依赖和配置复杂度；当前只需要轻量控件博物馆。放弃。
- **一次性抽出 `web/src/components` 全部内容**：表面整齐，但会把业务壳层和 API 依赖带进通用包。放弃。
