# ADR-106: 业务能力整体退役，JM 收窄为纯透传通道

- **日期**: 2026-10-23
- **状态**: accepted
- **取代**: ADR-025（ServerProbe 全能业务 agent 的部分决策）、ADR-026（业务适配器 manifest）、ADR-027（业务命令桥寻址）、ADR-028（业务数据存储策略）、ADR-029（业务高危写确认）——**仅取代其在 JM 侧的业务实现部分；ServerProbe 侧的数据面机制仍然有效**
- **相关**: FR-521~537、ADR-104（danger gate）、ADR-105（AI 助手在 Go CP 内）

## 上下文

JM 第五期 JBIS 业务对接平台（FR-115~127，v0.10.0~v0.14.0 交付）把经济与背包的业务语义收进了平台：

- 三张业务表：`business_events` / `economy_balance_mirrors` / `economy_ledger_entries`
- 业务事件落库、镜像维护、聚合查询（`service/business_events.go`）
- 四个业务读接口（`router/business_event.go`）
- 业务定制页（经济台、背包卡）

这些能力带来了三个持续存在的问题：

1. **语义越界**：JM 开始理解 `economy` / `inventory` 的含义，每加一个业务域就要改平台代码、加表、加接口
2. **发版耦合**：业务 UI 改动需要重编译整个 Go 二进制（`go:embed`），活动这类高频迭代的业务被平台发版节奏绑死
3. **真源混淆**：`EconomyBalanceMirror` 虽是镜像，但它与插件库的关系需要靠注释和文档维持，实际运维中容易被误认为真源

与此同时，分层定位逐渐清晰：

- **Beacon** = 集群路由控制面（拓扑/调度/消息/健康/身份）
- **JM** = 基础设施 + 通道 + 配置中心
- **ServerProbe** = 数据面中介（只做路由，不认识任何业务）
- **业务台**（独立部署）= 业务语义与业务数据的唯一持有者

ServerProbe 侧已完成同方向的重构（ADR-0030：移除内置集成，改为第三方自注册），证明"平台不做业务"这条路可行。

## 决策

### 1. JM 侧业务能力整体退役

删除全部业务语义产物：

| 对象 | 处置 |
|---|---|
| `BusinessEvent` / `EconomyBalanceMirror` / `EconomyLedgerEntry` | 删表，**不备份**（用户明确决策） |
| `service/business_events.go` | 整文件删除 |
| `router/business_event.go`（四个读接口） | 整文件删除 |
| `docs/specs/business-integration/` | 归档，不删除（保留历史） |
| `docs/adr/025~029` | 保留原文，追加取代标注（ADR 只追加不删） |

### 2. 保留并强化纯透传通道

JM 只保证三件事：

- **命令能到**：`POST /instances/:id/business`（通用 `domain.verb` 转发）
- **回执能回**：原样透传插件返回
- **事件能转**：SSE 原样转发，不解析 payload

配套新增：批量命令（分组粒度 + 跨区确认）、对账协调（拉取透传）、桥能力接入、只读统计契约。

### 3. 边界铁律（写入 PRD 与代码 review 清单）

> JM 不理解任何业务语义——不定义动作名、不规定 payload/output 字段、不解析 manifest 内容。

具体化：

| 允许 | 禁止 |
|---|---|
| 记录通道事实（actor/target/domain/verb/requestId/result/duration） | 记录 payload / output 内容 |
| 按 `domain` 做不透明标签分组统计 | 按 domain 做业务语义归类或阈值告警 |
| 原样透传 manifest | 解析 manifest 并据此做业务决策 |
| 提供事件的短期环形缓冲（非持久） | 做长期存储或聚合 |

### 4. 审计的边界

审计只记通道事实，payload 与 output 一律不入审计。理由：

- 可能含玩家数据、密钥、PII
- 一旦记录，就会有人问"能不能按 payload 搜索"，然后长出业务查询能力

### 5. 数据精准的三重保障

放弃"JM 存业务数据"后，一致性靠：

| 机制 | 作用 |
|---|---|
| `dedupKey`（插件生成） | 至少一次投递下的幂等去重 |
| `seq`（探针生成，传输层） | 检测事件缺口 |
| 对账（业务台主动触发） | 兜底修正偏差 |

**JM 在这三者中只做透传，不参与任何计算。**

### 6. 配置能力反向迁入

本 ADR 同时确认：Beacon 的配置中心与交付编排迁入 JM（FR-529~533），Beacon 侧保留默认关闭的开关（FR-281）。

理由：配置是"静态内容"，与文件/进程同类，属于 L1 基础设施职责；Beacon 的 in-process agent 在服务器离线时无法下发配置，天然不可靠。

## 理由

### 为什么业务必须移出平台

- **发版节奏**：业务迭代远快于平台，`go:embed` 单二进制让每次业务改动都要重编译
- **语义膨胀**：每加一个业务域就加表加接口，平台被业务拖着走
- **可替代性**：ServerProbe 的 `domain.verb` 通道已经足够通用，平台无需理解语义

### 为什么保留通道而不是彻底断开

业务台需要一条稳定、有审计、有幂等、有权限的通道访问插件。让业务台直连服务器意味着重做 NAT 穿透、认证、审计、限流——成本远高于保留通道。

### 为什么删表不备份

用户明确决策。V1 业务数据属于早期实验性质（经济域与背包域仅在少数环境验证），没有生产依赖。

### 为什么审计不含 payload

这是保持"纯透传"定位的关键。一旦审计记录 payload，JM 就重新承担了业务数据的存储与查询责任。

## 后果

### 正面

- JM 代码量下降，职责单一，后续业务迭代不再改动平台
- 业务台可独立发版，UI 改动不触发平台重编译
- 三个系统的边界可用一句话说清，新人可快速判断"功能该放哪"
- 配置真源唯一（Beacon 关闭后）

### 负面与代价

- **业务台成为新的大工程**：活动/商城/邮件 + 自有库 + 对账逻辑全部要新建
- **一次性迁移成本**：存量业务表删除、配置数据迁移（FR-533）
- **运维复杂度上升**：从 2 个系统变成 3 个（不含 Beacon 可选）
- **对账逻辑的正确性**由业务台承担，平台不再兜底

### 风险

| 风险 | 缓解 |
|---|---|
| 业务台实现质量决定数据一致性 | 提供 dedupKey + seq + 对账三重机制，业务台按规范实现 |
| 配置迁移丢数据 | FR-533 要求 dry-run 报告 + 版本链完整性核对 + 2 周回退窗口 |
| 边界随时间腐化 | FR-528 要求把边界写入 API 文档；FR-283 要求写入架构文档；代码 review 检查 |

## 关系

- **ADR-025**：其"ServerProbe 是唯一全能业务 agent"的定位**继续有效**；但"JM 作为业务总管"的部分被本 ADR 取代
- **ADR-026/027**：业务适配器与 `domain.verb` 寻址机制**继续有效**（这是通道层），但其在 JM 侧的落库与聚合实现被移除
- **ADR-028**：业务数据存储策略被本 ADR 取代——JM 不再存任何业务数据
- **ADR-029**：高危写确认机制**继续有效**（属横切能力，与业务无关）
- **ServerProbe ADR-0030**：同方向（移除内置集成），两仓协同
- **FR-281~283（Beacon）**：配置能力开关关闭，与本 ADR 的"配置迁入 JM"配套

## 实施顺序

```
FR-521 退役业务能力
  ↓
FR-522 事件透传 → FR-523 批量 → FR-524 写穿
                        ↓
                   FR-525 对账
  ↓
FR-526 桥接入 → FR-534 插件面板
FR-527 统计契约 → FR-528 API 规范
FR-529 配置分层 → FR-530 落盘 → FR-531 灰度 → FR-532 生效 → FR-533 Beacon 迁移
```

配置迁移（FR-533）必须在前四项完成后启动，否则会出现"两个系统都有半套配置能力"的最坏状态。
