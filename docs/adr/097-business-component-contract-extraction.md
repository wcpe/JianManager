# ADR-097: 应用业务组件受控化并入 @jianmanager/ui

- **日期**: 2026-10-06
- **状态**: accepted
- **关联**: FR-502（本决策的落地项）· 增强 ADR-064（第一方 JS 库形态）· 承接 FR-496~501（组件库重构批）· 取代无（实际是 ADR-058「组件博物馆」价值的兑现路径）

## 上下文

主控台（`apps/control-plane-web`）的组件库重构已推进到第 6 阶段，`packages/ui` 现含 31 个原语 + 9 个布局 + 6 个导航外壳 + 7 个图表 + 13 个受控业务视图（原 `packages/biz-views`，本轮并入）+ 51 个纯逻辑模块。但**主控台自身的业务组件仍全部留在应用内**，共 177 个（其中 26 个是 `components/ui/` 兼容再导出层，不计）。

「直接把剩下的组件搬进包」这条捷径已被实测证伪——真正零应用依赖的只有 16 个：

- 7 个是 `components/charts/*` 的两行再导出层（本就不该迁）
- 2 个是 `devtools/` 的 mock 调试面板（开发工具，不该迁）
- 12 个已在前批迁走
- 余下被相对路径 / `sonner` / devtools 定位挡住

其余 151 个组件的依赖分布（实测）：

| 依赖 | 数量 | 性质 |
|---|---|---|
| `@/api`（自行取数） | **128** | 其中纯读取 74、含写操作 54 |
| `sonner`（toast） | 55 | 副作用 |
| `react-router` | 32 | 路由身份 |

也就是说，**挡住迁移的不是耦合深度，而是「所有权边界」**：这些组件自己决定何时取数、何时弹提示、从哪读路由，一旦进入共享包，就等于把「取数时机」这类应用侧决策固化进了设计底座。原 `biz-views` 的硬约束（不取数、不碰路由、不发请求、不弹 toast）之所以有效，是因为它只收留了天然满足该约束的组件；现在要覆盖剩余的，只能**改造**它们。

同时存在一个反向压力：组件博物馆（`apps/ui-museum`）的目标是「全部件 + 全主题」验证台，但业务组件若不进包，博物馆就看不到它们——而业务组件恰恰是最需要跨主题/跨明暗验证的部分（它们组合最复杂、样式最易漂移）。

## 决策

1. **采用 a+b 双范式，按组件性质二选一**（不用「抽 `packages/api`」的 c 方案）：
   - **a 范式 · 外壳取数 + props 注入**：适用于 74 个纯读取组件。数据与加载/错误态由外壳调用 hook 后经 props 传入，组件只负责展示与本地 UI 状态（过滤词、折叠、选中项等 **UI 状态留在包内**，只有「取数结果」经 props 注入）。
   - **b 范式 · 受控 + 回调注入**：适用于 54 个含写操作组件。组件持有 UI 状态，用户动作以 `onXxx` 回调上报（如 `onEvict(sha)`、`onSaveCap(bytes)`），由外壳执行 mutation、决定成功/失败文案与 toast。
2. **沿用原 `biz-views` 的硬约束，且对全部视图生效**：包内**不得** import 应用的 `@/api`、`@/lib`、`@/components`，也不得依赖 `react-router`、`@tanstack/react-query`、`sonner`。该约束由包边界测试守门，不靠人工记忆。
3. **新增共享纯逻辑一律入包 `src/lib/`**，不随组件留在应用——避免「组件进了包、它依赖的工具函数还在应用里」的悬空依赖（前批已按此处理 `virtual-list`、`console-*` 等 21 个模块）。
4. **被多个业务组件共用的应用侧基础件优先迁包**，而非让每个组件各自重造。首个实例是 `DangerConfirm`（确认破坏性操作）：它是「对话框 + 危险语义 + 确认/取消」的通用件，业务组件依赖它，包内却不能引用它——故按本决策迁入包的视图层。
5. **目标位置**：`packages/ui/src/components/views/<域>/`，域名沿用应用的模块聚类（`console`、`explorer`、`client-dist`、`bot-load`、`file-browser`、`nodes`、`instances`…），使迁移前后目录语义可对照。
6. **分批顺序按 API 模块聚类**，而非按文件名字母序：`instances`(32) → `nodes`(19) → `metrics`(13) → 其余零散。理由是同域组件共享数据结构与 i18n 命名空间，同批处理可复用同一套 props 契约与测试夹具。
7. **首批以 2 个代表性组件走通端到端**（一读一写：`NodePortsPanel` 走 a、`NodeArtifactCachePanel` 走 b），验证 props 契约形态、测试改动量与 toast/confirm 的归属后再批量推进。

## 理由

- **a/b 的划分依据是「决策归属」，不是「代码复杂度」**：读操作的本质是「何时取、取几次、缓存多久」——这是应用侧的策略；写操作的本质是「出错怎么办、成功提示什么」——同样是应用侧策略。两者都不该由设计底座决定。
- **c 方案（抽 `packages/api`）自相矛盾**：它能最快覆盖全部 128 个，但那样组件仍在包内自行取数，只是把 `@/api` 换成合法包名——受控化目标（包不取数）被绕过而非达成，且 74 个纯读组件本可零成本受控化，包内取数是过度设计。
- **UI 状态留在包内、数据经 props 注入的分界是可判定的**：判断标准是「该状态是否随应用运行时而变化」——过滤词不随路由变化，routeKey 随；故前者留包内，后者注入。这条界线让 a 范式不必把组件阉割成纯展示。
- **同域聚类分批能摊薄契约设计成本**：同域组件的数据结构同源（如 instances 域的 `InstanceInfo`），一批内的 props 形态可保持同构，评审与测试也更集中。

## 后果

- **外壳变厚是必然代价**：每个使用点需自行取数并传 props。这换来的是组件可在博物馆（无后端、无路由）独立渲染——即「组件可被单独验证」这一能力。
- **每个组件的 props 契约需重新设计**：不是机械改写 import。74 个纯读组件的契约形态趋同（`data` / `isLoading` / `isError` + 可选 `active`）；54 个写组件的回调签名逐个设计，是本轮主要成本。
- **toast 从组件内消失**：成功/失败文案由外壳决定。包内不再出现 `toast.success(...)`，改由回调的返回值或外壳侧的状态驱动。
- **包边界测试需扩展**：现有 `ui-package-boundary.test.ts` 的清单是「首波」，随迁移推进需补入新成员，并新增「视图层不得依赖 router/react-query/sonner」的断言。
- **`@/lib` 的共享模块随之迁包**：如 `artifact-cache`、`instance-prefetch`、`client-dist-query` 等，应用侧改为从包取（沿用前批「归包、两边都从包取」的做法，而非跟着某个组件移动）。
- **迁移期间目录双写不引入**：应用内旧组件在迁走的同一次提交中改为从包再导出或直接被引用替换，不留两份实现（避免此前出现过的「包内实现成死代码而应用用副本」那类静默分叉）。
- **本决策不改变任何页面行为**：数据口径、权限、深链、文案一律保持；属行为保持的重构。

## 备选（未采纳）

- **c：抽 `packages/api`，组件继续自行取数**：覆盖最快但绕过受控化目标，且把取数策略固化进包（见「理由」）。
- **只做 a 范式（74 个纯读），写组件留在应用**：把「组件库是否完整」变成依赖组件性质的偶然结果，博物馆仍看不到半数业务组件；且写组件往往与读组件同域成对出现（如实例详情卡片与它的操作），拆开会让同一域跨两处维护。
- **纯移动 + 应用侧保留一份 wrapper**：wrapper 会重复 props 透传与事件绑定，等于把「同一个组件的两种写法」并存，长期必然漂移。
- **让包内直接依赖应用的 API 层（通过依赖倒置容器注入 query client）**：技术上可行，但把 React Query 的运行时语义（缓存键、失效策略、重试）泄漏进设计底座，与 ADR-064 划定的「第一方库」边界冲突。

## 关系

- **增强 ADR-064**：第一方 JS 库的形态（`packages/*`）不变，本决策只把它的成员从「原语」扩展到「受控业务视图」。
- **承接 FR-496~501**：那批工作的结论是「组件库自包含 + 布局规范 + 导航外壳」，本决策延续同一方向处理其未覆盖的「业务组件所有权」问题；那批判定的「不新增 ADR」是基于其范围不涉及新的架构取舍，本决策则确实改变了包与应用的边界定义，故单独成文。
- **兑现 ADR-058**：组件博物馆从「原语陈列」升级为「全部件验证台」，其前提正是本决策——组件必须能在无后端、无路由的环境下渲染。
- **FR-502**（本决策的落地项）：应用业务组件受控化迁入 `packages/ui`。
