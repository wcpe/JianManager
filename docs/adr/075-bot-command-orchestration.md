# ADR-075：Bot 命令编排与动作成功边界

- **日期**：2026-07-20
- **状态**：accepted
- **关联**：ADR-006、ADR-074
- **取代/修订**：仅取代 ADR-074 中 Bot 命令业务成功真源的相关决策；不取代其三进程模型、Control Plane 调度、目标实例与 Worker 执行节点解耦等决策

## 上下文

Bot 命令由 Control Plane 编排并路由到执行节点，最终由 Bot Worker 调用 Mineflayer 的 `bot.chat` 发送。一次发送之后，服务器是否接受命令、发送者是否具备权限，以及命令是否产生预期业务效果，可能需要依赖服务端实现、权限系统或业务事件才能判断。

命令动作需要一个不绑定具体项目、玩法或服务端探针的稳定成功边界。若把服务端接受、权限判断或业务效果作为通用同步成功条件，命令链路将与具体服务器实现耦合，并且无法为所有命令提供一致证明。

## 决策

1. **`bot.chat` 调用成功即命令动作成功**
   - Bot Worker 成功调用 `bot.chat`，且调用过程没有同步抛出错误，即认定本次命令动作成功。
   - 该成功只表示 Bot Worker 已按请求完成聊天或命令发送动作。

2. **不验证服务端结果**
   - 命令动作成功不证明服务器已经接受、解析或执行该命令。
   - 命令动作成功不验证 Bot 是否具备相应权限。
   - 命令动作成功不验证命令是否产生预期业务效果。

3. **编排层沿用动作结果**
   - Worker 与 Control Plane 传递并汇总 Bot Worker 返回的命令动作结果，不将缺少服务端确认解释为失败。
   - 调用 `bot.chat` 前的路由、进程通信或参数处理失败，以及调用时同步抛错，仍按命令动作失败处理。

4. **服务端验证是可选扩展**
   - 未来可通过额外的事件、适配器或 ServerProbe 扩展服务端接受、权限或业务效果验证。
   - 此类验证属于独立的业务观测结果，不改变通用命令动作成功语义，也不是命令发送链路的必需依赖。

## 理由

- `bot.chat` 是 Bot Worker 可直接控制和一致观测的发送边界。
- 服务端接受、权限和业务效果没有跨项目通用且可靠的确认协议。
- 将动作成功与业务效果分离，可保持命令编排能力独立于具体项目、玩法和 ServerProbe。
- 可选观测能力可以按业务需要演进，而不改变基础命令接口的成功语义。

## 后果

- 调用方收到命令动作成功时，只能确认发送动作已完成，不能据此宣称服务端执行成功。
- 需要证明权限或业务效果的场景，必须单独消费相应的服务端观测结果。
- ServerProbe 缺失或不可用不会影响通用 Bot 命令动作的成功判定。
- 错误信息和界面文案应区分“命令动作失败”与“服务端业务验证失败”。

## 与 ADR-074 的关系

本 ADR 仅取代 ADR-074 中将业务成功依赖持续事件或其他服务端证据的真源部分。ADR-074 确立的三进程模型、Control Plane 全局调度、Worker 节点容量与运行时职责、目标实例与执行节点解耦、跨节点路由及批量幂等协议继续有效。

## 否决方案

### 将服务器响应作为通用同步成功条件

不同服务端、插件和命令没有统一响应格式，无法形成可靠的通用判定，否决。

### 将权限或业务效果作为命令动作成功条件

权限和业务效果属于服务端领域，依赖具体项目与业务语义，会使基础命令链路失去通用性，否决。

### 强制依赖 ServerProbe 验证

ServerProbe 不是所有目标环境的必备能力，强制依赖会扩大部署前提并耦合命令发送与业务观测，否决；仅保留为未来可选扩展。
