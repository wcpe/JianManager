# ADR-098: 业务视图与业务契约退回应用，组件库回归设计系统

- **日期**: 2026-10-09
- **状态**: accepted（2026-10-10 由 [ADR-099](099-danger-gate-self-judged.md) 修订：保留的 a+b 范式中「角色门禁由外壳注入」一环改为由组件自行判定，其余不限）
- **关联**: 取代 [ADR-097](097-business-component-contract-extraction.md) · 撤销 FR-502 的落地方向 · 回归 ADR-064 划定的第一方库边界 · 保留 ADR-058（组件博物馆）但收窄其范围

## 上下文

ADR-097（2026-10-06 accepted）决定把主控台的业务组件按 a+b 双范式受控化后并入 `@jianmanager/ui`，并把随迁的共享纯逻辑一并入包 `src/lib/`。该决策已按批推进：截至撤销前，`packages/ui` 含 270 个业务视图 `.tsx`（39 个域目录 + 17 个顶层零散视图）与 187 个业务 lib 模块，应用侧对应位置只留两行再导出 shim，业务调用点改从包取。

推进过程中暴露出该方向与产品意图的偏离：

1. **组件库的定位被改变**。`packages/ui` 原本是设计系统（原语、布局、图表、样式、通用工具）；ADR-097 之后它同时承担了业务职责——包内出现 `instance`、`console`、`client-dist` 等域概念，包的体积、依赖面（`@codemirror/*`、`fflate`、`react-qr-code`、`react-grid-layout`、`react-markdown`、`remark-gfm` 等业务视图专用依赖）与变更频率都随之膨胀。
2. **应用侧的「接线层」被抽薄**。业务组件迁包后，应用侧只剩取数与 toast 接线，页面逻辑被拆到两个仓库位置，同一功能的改动需要在包与应用之间来回。
3. **组件博物馆的收益与代价不成比例**。ADR-097 的主要动因是「让博物馆覆盖业务组件」，为此付出的代价是整个业务前端被搬进共享库；而博物馆本身是开发期验证工具，不值得让生产代码的归属迁就它。
4. **该方向的推动并非产品要求**。ADR-097 及其后的迁移批由 AI 会话自行发起并落库，产品侧未提出过「把业务组件并入组件库」的需求；产品侧的实际要求是「组件库只放组件与样式」。

## 决策

1. **撤销 ADR-097**。业务视图与业务契约的全部所有权退回应用侧：
   - 视图 → `apps/control-plane-web/src/components/views/<域>/`（域划分与 ADR-097 的目录语义保持一致，便于对照）
   - 业务 lib → `apps/control-plane-web/src/lib/`
2. **`packages/ui` 回归设计系统**，只保留：
   - 原语与布局（`components/`，含 `shell/`、`layout/`）
   - 图表（`charts/`）
   - hooks、样式（`styles/`）
   - **设计系统自用 lib 共 12 个**：`brush`、`chart-hover`、`color-contrast`、`combobox`、`focus-ring`、`interaction-overlay`、`monitor-metrics`、`stat-card`、`theme`、`threshold`、`tone`、`utils`
   其中 `focus-ring` 与 `color-contrast` 是回迁过程中补认的——前者被 `button`/`input`/`dialog` 等原语依赖，后者被博物馆的主题对比度矩阵使用，二者属设计系统而非业务。
3. **进包判据（今后新增模块一律按此判定）**：
   - 被至少两处复用，**或**纯展示且无业务语义；**且**
   - 不 import 应用的 `@/api`、`@/lib`、`@/components`，不依赖 `react-router`、`@tanstack/react-query`、`sonner`
   - **页面级视图不符合**，不得进包
4. **应用侧对包的依赖保持单向**（`apps/* → packages/ui`），由边界测试守门（见「后果」）。
5. **组件博物馆收窄为设计系统验证台**：移除五个业务视图分区（`views-console`、`views-client-dist`、`views-ops`、`views-admin`、`views-workflow`），只保留原语、布局、图表、表单、数据展示、Overlay、Monitoring、Tabs 等设计系统分区。

## 理由

- **归属应由「谁决策」决定，而非「能否受控化」**。ADR-097 的 a+b 双范式在技术上成立（组件确实被改造成不取数、不碰路由），但它解决的是「怎么搬」而不是「该不该搬」。业务视图的取数时机、权限口径、文案与深链语义都是应用侧决策，把它们移入共享库只是把决策点搬了位置，并未消除耦合。
- **设计系统的价值来自稳定与通用**。包的消费者越少、概念越抽象，越能被安全复用；一旦装入业务概念，任何业务改动都会触碰包，包的版本与依赖面被迫跟随业务膨胀。
- **单仓库内的「分层」比「跨仓库」更划算**。应用与包在同一仓库，业务视图放应用侧并不损失任何复用能力（应用内相对/别名导入即可），却避免了跨包改动、shim 维护与两处测试环境的适配成本。
- **博物馆的目标可由更小的代价达成**。博物馆需要的是「组件能在无后端、无路由环境下渲染」，这要求组件**受控**，但不要求组件**住在包里**。业务视图留在应用侧、保持受控形态，博物馆若要展示可在博物馆内引用应用侧组件——无需为此改变生产代码归属。

## 后果

- **回迁已完成**（本次撤销的执行结果）：
  - 视图：299 个文件（含测试）全部回到 `apps/control-plane-web/src/components/views/`
  - lib：231 个业务模块（含测试）回到 `apps/control-plane-web/src/lib/`
  - 包入口 `index.ts` 从约 640 行缩到 99 行，只导出设计系统
  - 包依赖从 17 个减到 5 个（`class-variance-authority`、`clsx`、`lucide-react`、`recharts`、`tailwind-merge`）
- **应用侧旧路径的再导出 shim 已由真实实现替换**，业务调用点保持原路径与原导出名，页面行为未变（数据口径、权限、深链、文案一律保持）。
- **`@/lib/<X>` 与 `@jianmanager/ui/lib/<X>` 的分工**：前者是应用自有业务逻辑，后者仅剩上述 12 个设计系统模块。既有 `ui-package-boundary.test.ts` 仍守「设计系统模块必须经包访问」，不因回迁放宽。
- **新增 `ui-package-rollback.test.ts`** 固化本次边界：包内无业务视图目录、不导入应用代码、lib 只剩设计系统模块、包入口不导出业务、依赖无业务残留、应用侧视图目录齐全。
- **ADR-097 的 a+b 双范式**作为**组件写法**保留（受控视图 + 外壳注入仍是应用侧组织业务组件的方式），但其**「并入组件库」的归属决策**被本 ADR 撤销。
- **FR-502 的验收口径随之改变**：不再要求「151 个组件全部迁入包」，改为「业务视图在应用侧、包内零业务」。
- **博物馆的业务视图分区已删除**，若将来需要业务组件的跨主题验证，应另行设计（例如博物馆按需引用应用侧视图），不得以「博物馆需要」为由再次把业务代码并入包。

## 备选（未采纳）

- **保留 ADR-097，只把最「业务」的部分退回**：边界无法划线——`DangerConfirm` 这类通用件与 `InstanceConsolePageView` 这类页面级视图混在同一目录下，部分回退会长期停在半途。
- **保留包内视图，只在包上加 `exports` 子路径隔离**：隔离的是导入路径，不是所有权；包内仍持有业务概念，依赖面与变更频率问题不变。
- **把业务视图移到新的 `packages/biz-views`**：只是换了个包名，业务代码仍是「跨包共享」，仍需跨包改动与两套测试环境；且应用是唯一消费者，独立包没有收益。
- **保留 ADR-097 的 lib 归包部分**（视图退回、lib 留包）：lib 是视图的直接依赖，视图回迁而 lib 留包会造成「视图在应用、它依赖的工具在包」的悬空关系，且这些 lib 同样含业务概念（`instance-*`、`console-*`、`client-dist-*`）。

## 关系

- **取代 ADR-097**：ADR-097 的全部决策（a+b 双范式并入包、共享纯逻辑入包、目标位置 `components/views/<域>/`、分批顺序）不再有效；其正文按 ADR 惯例保持原样，仅状态行标注被取代。
- **回归 ADR-064**：第一方 JS 库（`packages/*`）的形态不变，本 ADR 把它的成员范围收敛回「设计系统」。
- **收窄 ADR-058**：组件博物馆作为设计系统验证台的定位不变，但其「全部件验证台」的目标范围收窄为设计系统组件。
- **FR-502**：该 FR 的落地方向由本 ADR 撤销，验收口径改为「业务视图在应用侧、包内零业务、边界测试守门」。
