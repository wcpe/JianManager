# ADR-107: 业务事件位点账本——不落 payload 的可恢复投递

- **日期**: 2026-10-25
- **状态**: accepted
- **关联**: FR-522（事件透传）、FR-525（对账）、ADR-106（业务能力退役）
- **背景方**: Loom `docs/API.md §9.1` 要求「JM 侧落库后再转发，消费方离线时事件不能消失」

## 上下文

四仓联调时出现一个**方向相反的硬性要求**：

| 方 | 要求 | 理由 |
|---|---|---|
| **Loom** | JM 必须**落库后再转发**，不能只在内存中转 | Loom 靠事件流构建三层镜像；Loom 重启/离线期间的事件若丢失，镜像永久缺口，且无法自愈 |
| **JM（FR-522 / ADR-106）** | **不落任何业务数据**，内存环形缓冲（20 万条/30 秒），非持久、可丢，超窗回 `replay_gap` | 一旦 JM 存业务数据，就会长出业务查询能力，退回「平台做业务」 |

两边都不是写错了：Loom 的镜像需要可恢复性，JM 的定位禁止持有业务内容。这是**分层定位冲突**，不是实现缺陷。

### 冲突的实质

真正需要的不是「事件内容持久化」，而是**「投递可恢复」**：

- Loom 要知道「我漏了哪几条」——这是**位点问题**
- Loom 要能拿到漏掉的内容——这是**重新拉取问题**

把这两件事分开，冲突就消失了：**位点可以存（传输元数据），内容不存（业务数据）**。

## 决策

### 1. JM 引入「业务事件位点账本」（`business_event_cursor`）

只存**投递元数据**，不含 payload：

| 字段 | 说明 |
|---|---|
| `id` | 自增主键 |
| `stream_seq` | CP 分配的全局位点（与 SSE `id` 同源） |
| `instance_id` | 来源实例 |
| `domain` | 业务域 |
| `seq` | 探针分配的 per-domain 序号 |
| `dedup_key` | 插件提供的幂等锚点 |
| `occurred_at` | 事件发生时间（epoch ms） |
| `created_at` | CP 接收时间 |

**不含 `payload`**——这是与 ADR-106 的分界线：位点是「信封的运输单据」，payload 是「信封里的信」。

### 2. 写入异步、批量、不阻塞扇出

- 扇出热路径只做「预渲染字节 + 投递订阅者」，位点写入走独立批量队列（默认 500 条或 1 秒批量）
- 写失败只记 WARN，**不影响事件投递**（位点是恢复用的旁路，不是主链路）
- 队列有界（默认 10000），满则丢弃最旧并计数——位点丢失的后果是「保守多拉一次快照」，可接受

### 3. 新增「缺口查询」端点

```
GET /api/v1/business/cursor?instanceId=&domain=&fromSeq=&limit=
```

返回该 `(instance, domain)` 区间内**存在过的位点**。Loom 用自己的已收位点做差集，精确得到缺口。

**为什么不用「返回缺失区间」**：JM 不知道 Loom 收到了什么，无法单方计算缺口。让 Loom 做差集是唯一正确的信息来源。

### 4. Loom 侧的恢复协议

```
收到 replay_gap
  → GET /business/cursor 查缺口位点
  → 对每个受影响 (instanceId, domain) 调 POST /business/reconcile 拉快照
  → 用快照修正镜像，并把该 (instance, domain) 的水位推进到快照位点
```

**只对受影响的实例/域拉快照**，不是全量对账——这是位点账本相对「盲对账」的核心价值。

### 5. 内容重放的未来路径（不在本轮）

ServerProbe 的 `EventSpillStore` 已把可靠事件落盘（含 payload）。将来可实现：

```
POST /business/replay { instanceId, domain, fromSeq, toSeq }
  → 探针从 spill 读原始事件，经现有通道重发
```

**这是内容重放的正确归属**：内容在数据面（探针），不在控制面（JM）。JM 只转发。

本轮不实现，因为：① Loom 的快照对账已能保证最终一致；② 重放需要新通道语义与背压设计，应独立评审。

## 理由

### 为什么不选「JM 落库事件」（Loom 的原始要求）

- ADR-106 的红线是「JM 不存业务数据」。payload 就是业务数据。
- 一旦存了，紧接着的需求必然是「按 payload 字段查询」「按玩家聚合」——这正是 FR-521 花大力气退役掉的能力。
- 存储成本与生命周期（保留多久？归档到哪？）都是新的运维负担。

### 为什么不只选「盲对账」（不做位点账本）

- Loom 无法知道「漏了多少、漏了哪几个域」，只能定期全量对账
- 100+ 实例 × N 个域的全量快照开销远超一张位点表
- 位点表让恢复变成「精确定点」，这是数量级的差异

### 为什么位点表可以存

- 它等价于消息队列的 offset 索引，是**传输层状态**，不含业务语义
- JM 仍然「不理解 domain 是什么」，只把它当字符串标签
- 保留期可短（默认 7 天），因为它只服务「近期缺口恢复」

## 后果

### 正面

- Loom 获得**精确定点恢复**能力，镜像最终一致有保证
- JM 守住 ADR-106 边界，不新增任何业务查询面
- 位点表体量可控（100 实例 × 20 事件/秒 × 7 天 ≈ 12 亿行，需分表；实际按保留期与采样可大幅压缩）

### 负面与代价

- JM 新增一张表与批量写路径（运维面 +1）
- Loom 要实现缺口差集与定点对账逻辑（复杂度 +1）
- 位点表在高频场景需要分区/归档策略

### 风险

| 风险 | 缓解 |
|---|---|
| 位点表膨胀 | 默认保留 7 天 + 定期裁剪；按 `(instance_id, domain, stream_seq)` 建索引控制查询成本 |
| 位点写失败导致缺口不可检测 | 写失败只降级为「Loom 保守全量对账」，不会更糟 |
| 有人后续要求「顺便把 payload 也存了」 | **本 ADR 明文禁止**：payload 持久化的正确归属是 ServerProbe 的 spill，不是 JM |

## 关系

- **ADR-106**：本 ADR 是其边界的**精化**而非突破——位点不是业务数据
- **FR-522**：环形缓冲与 SSE 语义不变，本 ADR 只增加旁路账本
- **FR-525**：Loom 的定点对账复用其 `reconcile` 端点
- **ServerProbe FR-36**：位点账本依赖探针的 `seq`（per-domain 单调）与其 `seqEpoch`
