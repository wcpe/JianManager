# ADR-099: 危险操作的角色门禁由 DangerConfirm 自行判定

- **日期**: 2026-10-10
- **状态**: accepted
- **关联**: 修订 [ADR-098](098-business-views-return-to-app.md) 保留的 a+b 范式（仅门禁归属一环）· 部分撤销 [ADR-097](097-business-component-contract-extraction.md) 的「受控视图不自行判定权限」· 不变 FR-059 与「后端 RBAC 为最终防线」这条架构不变量

## 上下文

ADR-097 的 a+b 双范式规定：受控视图不自行判定权限，`DangerConfirm` 只接收 `allowed`，由应用侧外壳读登录态角色后注入。ADR-098 撤销了「业务组件并入组件库」的归属决策，但明确保留该范式作为组件写法——门禁归外壳这一点因此沿用至今。

这一设计有一个无法用类型或既有测试拦截的失效模式：**`allowed` 是可选 prop 且默认 `true`**。外壳漏传即静默放行——视图照常渲染确认弹窗，越权用户看到启用状态的确认按钮，只有在点下去被后端拒绝时才知道自己没权限。类型检查通过（可选 prop 不传是合法的），守卫用例也通过（它测的是组件本身，覆盖不到漏配的调用点）。

ADR-098 之后该范式的前提已经改变：视图不再位于组件库内，它本来就在应用侧，读应用状态没有任何归属问题。门禁留在视图外的唯一理由（组件库不持鉴权状态、需在无登录态环境如博物馆独立渲染）已随回迁撤销。

回迁完成后的核查证实了这个失效模式不是理论风险：**全仓 17 处调用声明了 `scope="platform"` 却没有接上 `allowed`**，其中包含清除节点缓存、重新注册节点、删除备份等平台级操作。这些调用点的作者意图明确（写了 `scope` 就是想拦），但门禁从未生效。`git log -S` 确认这些文件从未传过 `allowed`——是范式本身的漏配，不是某次改动引入的回归。

## 决策

**角色门禁收进 `DangerConfirm` 自身**：组件在声明了 `scope` 时自行调用 `useDangerPermission(scope)` 读登录态角色并判定，`allowed` prop 被删除。

具体地：

- `DangerConfirm` 不再接受 `allowed`；`denied` 由组件内部的判定结果与 `scope` 是否声明共同决定（未声明 `scope` 时不做前端门禁，维持既有语义）。
- `DangerScope` 定义移到契约侧 `lib/shared/danger.ts`——视图要 import 该模块的 hook，类型若留在视图会形成循环。
- 应用侧接线层 `components/common/DangerConfirm.tsx` 随之失去存在理由，删除；其 6 个消费者直连视图。
- 附带清理：ADR-097 范式下外壳为注入 `allowed` 而持有的 `useDangerPermission` 调用、以及 12 个视图上对应的 `dangerAllowed` / `revokeAllowed` / `unbanAllowed` 透传链全部移除。这些 prop 的唯一用途就是承载注入结果。
- **a+b 范式的其余部分不变**：受控视图仍然取数在外、纯 UI 状态在内、经 props 接收数据与回调。本 ADR 只改「角色判定住在哪」这一环，不是对范式的整体否定。

## 后果

- **漏配这一失效模式从结构上消失**：调用点只需声明 `scope`，判定与渲染在同一个组件内，不存在「声明了却忘了接」的中间态。新增调用点无需要记得注入任何东西。
- **视图从「完全受控」变成「知道登录态」**：这是有意的取舍。角色是渲染决策的一部分，把它推到外壳换来的是漏配风险，而收益（组件库不持鉴权状态）随 ADR-098 回迁已不存在。视图仍不取数、不碰路由，与 `@/api/*` 的隔离不受影响。
- **测试能覆盖到真实调用形态**：门禁守卫用例现在渲染的就是生产用的同一个组件，不再存在「用例过、调用点漏」的空档。
- **后端 RBAC 仍是最终防线**：本次不动这条不变量。前端门禁的定位仍是「提前禁用并说明原因」，改善的是越权用户被告知的时机，不是安全性。
- **新增三条架构断言**（`src/test/ui-package-rollback.test.ts`）：组件必须自行读登录态、不得再有 `allowed` prop、任何调用点不得注入 `allowed`。第三条用 `[\s{]allowed=` 而非 `\b`，避免把 `data-export-allowed` 这类 DOM 属性误判为注入。
- **测试登录辅助**：`loginMockUser()` 的默认 token 不是 JWT，`decodeJwt` 解不出 `role`，而 `canRunDanger` 对 `role=null`（未登录）判为拒绝。这对未登录语义是对的，但渲染带 `scope` 弹窗的用例必须给真实角色，故补 `makeTestJwt` / `loginMockUserAs`。三个受影响的既有用例改用之。

## 备选（未采纳）

- **保留注入，只补上那 17 处**：消除当前缺陷但保留范式——下一个调用点仍可能漏配，且没有任何机制能发现。缺陷的根因是范式的默认值（可选 + 默认放行），不是那 17 个文件的疏忽。
- **保留 `allowed` 但改为必填**：类型上强制注入，能拦住漏配。但代价是每个调用点都要读角色并传值，把一件本可自决的事变成每处重复的仪式；且 `scope` 与本该同源的 `allowed` 分处两地，仍可被传成互相矛盾的值。
- **去掉那 17 处的 `scope` 声明**：承认这些操作不做前端门禁、全靠后端兜底。改动最小，但放弃的是产品明确的意图（平台级操作应在 UI 上就拦住），且会让 `scope` 这个 prop 的语义变得不可信——同样写法有的拦有的不拦。
- **改成运行时告警（漏传 `allowed` 时 console.warn）**：只在不传时提示，传错了（如 `allowed={someString}`）仍静默放行；且告警在生产里没人看，不构成防线。

## 关系

- **修订 ADR-098**：该 ADR 保留 a+b 范式时，门禁归属一环照旧沿用 ADR-097；本 ADR 只改这一环，ADR-098 关于回迁归属、包边界、博物馆范围的决策不变。
- **部分撤销 ADR-097**：「受控视图不自行判定权限」这一条不再有效；ADR-097 的其余内容早已由 ADR-098 撤销。其正文按 ADR 惯例保持原样。
- **不变**：FR-059 的危险操作保护语义（二次确认、高危输入名校验、角色门禁范围分级）、以及「前端仅做 UI 拦截、最终拒绝由 Control Plane RBAC 强制」这条架构不变量。
- **FR-502**：与本次无关，其验收口径仍为 ADR-098 所定。
